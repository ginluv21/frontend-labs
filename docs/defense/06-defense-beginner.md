## 1. Какая идея у шестой работы

В пятой лабораторной мы научились получать данные. В шестой учимся распределять состояние между подходящими механизмами, переключать страницы и управлять серверными данными через кеш.

Сайт остаётся прежним по теме: вопрос сове и случайная цитата Канье. Добавляется общая копилка, в которую можно сохранить понравившийся текст.

Сценарий пользователя:

1. На главной задать вопрос и получить результаты.
2. Выбрать фильтр источника.
3. Нажать «В копилку» под текстом.
4. Дождаться успешного сохранения.
5. Перейти в копилку и увидеть запись.
6. Вернуться обратно, сохранив общий выбранный фильтр.

Копилка общая для посетителей сайта. Регистрации и разделения записей по аккаунтам нет. Локальная база ноутбука и база опубликованного сайта являются разными хранилищами.

## 2. Четыре инструмента простыми словами

| Инструмент | Что поручено ему |
| --- | --- |
| Zustand | Помнить общий выбранный фильтр |
| React Router | Определять страницу по адресу и выполнять переходы |
| TanStack Query | Организовывать запросы, состояния и кеш серверных ответов |
| Axios | Отправлять HTTP внутри функций query и mutation |

Эти инструменты не делают одно и то же. Их удобно представить как разные обязанности: выбранный режим, навигация, организация данных и транспорт сообщений. Это только аналогия, реальный код объясняется ниже.

Кеш - временно сохранённый результат, который можно использовать повторно. Он позволяет не обращаться к серверу при каждом быстром возвращении на уже открытую страницу. Кеш не равен постоянной базе: база хранит исходные записи, а кеш копию результата чтения.

### Базовые слова JavaScript и React, которые понадобятся дальше

Компонент - функция описания части интерфейса. JSX - похожая на HTML запись элементов внутри JavaScript, которую обрабатывает сборщик. Props - входные значения компонента. State - запоминаемые данные, изменение которых влияет на отображение. Рендер - вычисление описания интерфейса из этих значений; он не равен полному обновлению документа браузера.

UseState - хук локального состояния. Хук - функция использования возможностей React, вызываемая на верхнем уровне компонента или собственного хука в постоянном порядке. Setter - функция обновления state. UseEffect настраивает синхронизацию с внешней системой и может вернуть cleanup, то есть функцию очистки.

Promise представляет будущий результат асинхронной операции. Async-функция возвращает Promise; await ожидает его завершения внутри соответствующей функции, не замораживая весь интерфейс. Callback - функция, переданная другому коду для последующего вызова. Например, onSuccess выполнит библиотека после успешной записи.

API задаёт договор общения программ, HTTP передаёт запросы и ответы, JSON является текстовым форматом данных. GET обычно читает, POST передаёт тело для обработки. Ответ Axios находится в data. Эти базовые понятия продолжают действовать и после подключения TanStack Query.

## 3. Где именно находится состояние

Состояние - информация, которую приложение помнит и использует для поведения или отображения. У нас оно разделено так:

| Информация | Место хранения | Что будет при уходе со страницы |
| --- | --- | --- |
| Черновик вопроса | useState AdvicePage | Может сброситься при размонтировании |
| Последний отправленный вопрос | useState AdvicePage | Тоже локален этой странице |
| Ошибка пустого ввода | useState AdvicePage | Не является ошибкой API |
| Выбранный источник | Zustand | Сохраняется между клиентскими переходами |
| Ответ совы и цитата | TanStack Query | Могут остаться в кеше после ухода |
| Список копилки | TanStack Query | Может остаться в кеше, пока не удалён |
| Состояние кнопки сохранения | useMutation | Относится к конкретному экземпляру кнопки |
| Сохранённая запись постоянно | Серверная база | Не исчезает от размонтирования React |

Важно не сказать «теперь всё в Zustand». Это неверно. По заданию ответы API не должны дублироваться в общем клиентском store.

Локальное состояние принадлежит компоненту. Общее состояние нужно нескольким компонентам. Серверное состояние происходит из внешнего источника и требует загрузки, обработки ошибок и актуализации. Такое разделение помогает не поддерживать вручную несколько независимых массивов одних записей.

## 7. Демонстрация Zustand и понятие store

На главной выбираю «Только сову». Карточка Канье скрывается. Перехожу в копилку и показываю тот же выбранный фильтр.

> У переключателя и страниц один store. Изменение не нужно передавать вручную из каждой страницы в другую.

Store переводится как хранилище. В нашем случае это маленький объект данных и действий, доступный подписанным компонентам.

```javascript
import { create } from 'zustand'

export const useFilter = create(set => ({
  source: 'all',
  setSource: source => set({ source }),
}))
```

Разбираю:

1. Import получает create из установленной библиотеки.
2. Create создаёт store и возвращает хук useFilter.
3. Set предоставлен Zustand для обновления.
4. Source - текущая строка фильтра.
5. SetSource - действие изменения.
6. Export делает хук доступным другим файлам.

Инициализация расположена на уровне модуля, а не в функции App. Модуль - файл с импортами и экспортами. При обычном рендере уже импортированный модуль не выполняет создание store с нуля заново.

Селектор:

```javascript
const source = useFilter(state => state.source)
```

Селектор - функция выбора нужного фрагмента состояния. Здесь она получает весь state и возвращает одну строку. Отдельный селектор выбирает действие setSource.

Переключение:

```jsx
<select
  value={source}
  onChange={event => setSource(event.target.value)}
>
  <option value="all">Всех</option>
  <option value="owl">Только сову</option>
  <option value="kanye">Только Канье</option>
</select>
```

Select управляемый: значение приходит из store, событие отправляет новое значение туда же. Компоненты подписаны на изменение. Смена фильтра не меняет SQL-данные и сама по себе не создаёт GET: она меняет отображение уже загруженного массива.

## 8. Filter, map и фактическое использование общего значения

На главной используется последовательность filter и map. Filter выбирает, какие карточки оставить, map превращает оставшиеся объекты в элементы React.

Например, для учебного массива:

```javascript
const items = [
  { source: 'owl', text: 'Совет' },
  { source: 'kanye', text: 'Цитата' },
]
const visible = items.filter(item => item.source === 'owl')
```

Visible содержит только первый объект. Это новый массив, исходные записи не удалены из сервера или query-кеша.

На копилке:

```javascript
const items = (saved.data || []).filter(item =>
  source === 'all' || item.source === source
)
```

Fallback `|| []` нужен, когда данных ещё нет. All пропускает всех. При другом значении сравниваются источники. Это вычисляемый результат рендера, а не второй самостоятельный state.

> Store используют SourceFilter, AdvicePage и SavedPage. Между переходами его значение остаётся. После полного F5 новый документ начнёт с all: persistence мы не подключали, и задание этого не требует.

Persistence означает дополнительное сохранение состояния между полными перезапусками, например через браузерное хранилище. Оно отличается от простого существования store в памяти открытой страницы.

## 9. Router, route и NavLink

Показываю переходы по ссылкам, затем «Назад» и «Вперёд».

> Router связывает адрес и компонент страницы. Route - отдельное правило такого соответствия. Routes выбирает подходящее правило.

Фрагмент маршрутов:

```jsx
<Routes>
  <Route path="/" element={<AdvicePage />} />
  <Route path="/saved" element={<SavedPage />} />
  <Route path="*" element={
    <section className="result">
      <h2>Сова сюда не допрыгала</h2>
      <p>Такой страницы нет.</p>
      <NavLink to="/">На главную</NavLink>
    </section>
  } />
</Routes>
```

Разметка здесь перенесена по строкам для чтения, смысл соответствует App шестой версии. Path задаёт адрес, element - элемент страницы. Звёздочка является запасным совпадением для неизвестного пути.

NavLink выполняет внутренний переход и сообщает активность ссылки. CSS может выделить класс active. У корневой ссылки end ограничивает активность точным соответствием корню.

SPA означает single-page application: приложение переключает представления внутри уже загруженной оболочки. Это не запрет иметь разные URL. Навигация Router позволяет иметь разные адреса без повторного скачивания целого HTML-документа на каждом обычном переходе.

## 10. Прямая ссылка, fallback и жизненный цикл

Открываю `/saved` напрямую и обновляю её.

> При прямом открытии сервер получает этот путь до запуска React. Поэтому должен вернуть HTML приложения. Потом Router выберет SavedPage.

Fallback - запасной вариант обработки. Наш Worker ищет ресурс, а для обычного пути без точки в последнем сегменте использует index.html. Для `/api/...` и отсутствующих файлов предусмотрена другая обработка, чтобы не отправить HTML вместо JSON или JavaScript.

Неизвестная обычная страница показывает клиентское сообщение, но HTML при этом может иметь HTTP 200. Это отличается от настоящего серверного 404 для отсутствующего ресурса. Нельзя сказать, что сам React автоматически выставляет серверный статус.

Mount - подключение компонента к дереву. Unmount - его удаление. При уходе с главной локальные question и submittedQuestion могут сброситься. Общая оболочка, store и QueryClient остаются выше переключаемых страниц. Поэтому сохраняются не все значения подряд, а только те, чьё место жизни это позволяет.

## 11. QueryClient и Provider

> В пятой работе запросы организовывал собственный эффект и useState результатов. Теперь данные и их сетевое состояние управляются TanStack Query.

```javascript
export const queryClient = new QueryClient({
  defaultOptions: {
    queries: { staleTime: 60000, retry: false, refetchOnWindowFocus: false },
    mutations: { retry: false },
  },
})
```

QueryClient - объект управления кешем и запросами. New создаёт экземпляр класса. Этот вызов расположен вне рендера, поэтому кеш не пересоздаётся при каждом изменении поля или маршрута.

Provider - компонент, предоставляющий общую возможность вложенным компонентам через контекст. Контекст позволяет получить нужный объект без передачи одного и того же prop через каждый промежуточный компонент.

```jsx
<QueryClientProvider client={queryClient}>
  <BrowserRouter>
    <App />
  </BrowserRouter>
</QueryClientProvider>
```

UseQuery и useMutation получают этот клиент. BrowserRouter даёт доступ к адресам и истории. Вложенность оборачивает App сразу двумя разными возможностями; один провайдер не заменяет другой.

## 12. Query: чтение данных и query key

```javascript
const owl = useQuery({
  queryKey: ['advice', 'owl', question],
  queryFn: ({ signal }) => getOwl(signal, question),
})
```

Query - управляемое описание получения данных. QueryFn - функция загрузки. Она возвращает Promise с результатом или выбрасывает ошибку. Axios находится внутри вызываемой API-функции.

QueryKey - идентификатор данных в кеше. Он не является URL запроса, React key списка или первичным ключом SQL. Эти три вида ключей решают разные задачи.

У нас:

| Ключ | Значение |
| --- | --- |
| `['advice', 'owl', question]` | Ответ на конкретный отправленный вопрос |
| `['advice', 'kanye']` | Последняя загруженная случайная цитата |
| `['saved']` | Общий серверный список копилки |

Вопрос влияет на ответ совы, поэтому входит в ключ. На цитату Канье вопрос не влияет. Фильтр не входит в ключ копилки, потому что сервер отдаёт один общий массив, который фильтруется уже в браузере.

Signal - сигнал отмены, предоставленный query-функции. Мы передаём его Axios. Самостоятельный контроллер эффекта пятой работы больше не нужен. Отмена клиентского ожидания при этом не гарантирует остановку любой уже начавшейся внешней генерации на сервере.

## 13. Почему ввод не отправляет запрос на каждый символ

Question хранит черновик, submittedQuestion отправленное значение. Query получает второе. Поэтому ввод меняет поле, но не ключ запроса до корректной отправки.

При новом вопросе setSubmittedQuestion вызывает новый рендер с новым queryKey. Query загрузит или найдёт данные нужного вопроса. Если такой вопрос уже есть в свежем кеше, повторное обращение к нему может использовать кеш.

При отправке того же текущего вопроса ключ не поменялся бы. Поэтому обработчик явно вызывает reload. Канье при новой отправке обновляется отдельным refetch, потому что его собственный ключ не менялся.

Refetch - повторное получение текущего query. Он не меняет вопрос в ключе. Если пользователь после ошибки отредактировал черновик без отправки, повтор карточки всё ещё использует submittedQuestion.

Сетевой useEffect заменён query-хуками. Эффект интервала совы остаётся: это работа с таймером, а не обход библиотеки запросов. UseEffect не запрещён вообще, меняется его роль в загрузке данных.

## 14. Pending, fetching, success и error

У query есть информация о данных и отдельно информация о выполнении запроса. Эти понятия важно не смешивать.

- IsPending показывает состояние, в котором ещё нет готового успешного набора данных. Обычно это первоначальная загрузка; без сети выполнение может быть приостановлено.
- IsFetching означает, что загрузка выполняется сейчас, в том числе повторное обновление уже известных данных.
- IsSuccess обозначает успешный результат.
- IsError обозначает ошибочный результат.

В useAdvice эти свойства переводятся в знакомые карточке loading/success/empty/error. Empty определяется длиной успешного массива. Это собственное представление приложения, а не обязательный встроенный статус с таким названием в TanStack Query.

На главной старый ответ во время обновления скрывается нашим преобразователем. На копилке прежние записи могут оставаться вместе с сообщением обновления или ошибки. Кеш библиотеки и решение UI о том, что временно показывать, не являются одним действием.

## 15. Как демонстрировать кеш

Открываю копилку, жду успешный GET, очищаю журнал Network, перехожу на главную и быстро возвращаюсь.

> Данные ещё свежие, поэтому список берётся из памяти QueryClient и новый GET не нужен.

StaleTime 60000 означает 60 секунд свежести. Fresh значит свежий, stale значит устаревший. Через минуту запись не обязана исчезнуть и запрос не обязан автоматически начаться ровно в этот момент. Нужно событие, например открытие устаревшего query или ручной refetch.

GcTime связан с удалением неактивного кеша. Неактивный query - тот, на который сейчас нет активной подписки страницы. В браузерной конфигурации мы не меняем стандартное значение около пяти минут. Это другой срок, не та же минута.

Retry:false отключает автоматические попытки после ошибки, но оставляет ручные. RefetchOnWindowFocus:false отключает обычное обновление из-за возвращения фокуса окна. Другие причины запроса, например восстановление соединения, отдельно не переопределены.

Не нажимай F5 для проверки быстрого перехода: F5 создаёт новый документ и новый QueryClient. Выключатель HTTP-кеша DevTools не равен выключению query-кеша. HTTP-кеш относится к протоколу, query-кеш к памяти JavaScript-библиотеки.

## 16. Mutation: серверная запись

На главной нажимаю «В копилку» под готовым текстом. Показываю POST, состояние ожидания и заблокированную кнопку.

```javascript
const save = useMutation({
  mutationFn: saveAdvice,
  onSuccess: () => client.invalidateQueries({ queryKey: ['saved'] }),
})
```

Mutation - управляемая операция изменения данных. MutationFn - функция, выполняющая её HTTP-запрос. Само объявление useMutation не сохраняет совет: оно готовит объект действия и его состояния.

Запуск:

```javascript
save.mutate({ source, text })
```

Mutate принимает конкретные аргументы и запускает запись. У кнопки есть isPending, isError и isSuccess. Disabled запрещает повтор до завершения. В обработчике дополнительно проверяется состояние.

После ошибки можно нажать снова. После успеха текущая кнопка показывает «Сохранено» и недоступна. Но статус относится к экземпляру компонента: после размонтирования новый экземпляр не обязан помнить прошлый успех. Серверная запись существует отдельно.

Почему генерация совы использует query, хотя отправляется POST? Query и mutation определяются назначением в приложении, а не одной буквой HTTP-метода. Генерация получает ответ по вопросу, а отдельный POST /api/saved создаёт сохраняемую запись. Повторная генерация расходует внешний ресурс, поэтому мы отключили нежелательные автоматические повторы и учитываем кеш.

## 17. Инвалидация: самая важная связь

OnSuccess - callback после успешного действия. Callback - переданная функция, которую вызовет библиотека в нужный момент. После записи он сообщает: список saved теперь может быть старым.

InvalidateQueries - пометка связанных query как неактуальных. Она не выполняет SQL INSERT сама, не очищает базу и не означает обновление всего документа браузера.

Если список активен, он может обновиться сразу. Если открыта главная, SavedPage не смонтирована: кеш только помечается, а GET придёт при переходе в копилку. Поэтому отсутствие GET немедленно после POST в нашем сценарии нормально.

Демонстрация:

1. До этого получить копилку, чтобы у неё был свежий кеш.
2. На главной сохранить новый текст.
3. Перейти в копилку раньше 60 секунд.
4. Показать новый GET и новую запись.

Свежесть была отменена инвалидацией. Если текст уже существовал, число строк может не увеличиться из-за защиты от дубликатов; для наглядной демонстрации выбирай новый текст.

OnSuccess в нашем коде возвращает Promise invalidateQueries. Библиотека может учитывать его завершение, прежде чем закончить обработку mutation. Мы не выполняем optimistic update - предварительное добавление до подтверждения сервера. Такой вариант потребовал бы отката при ошибке, а для этой работы достаточно ожидания и инвалидации.

## 18. Сервер, SQL и постоянная копилка

Сервер получает GET для чтения и POST для добавления по одному адресу /api/saved. У записи только id, source и text.

SQL - язык обращения к таблицам базы. Таблица состоит из строк записей и колонок полей. SQLite - локальный SQL-движок. D1 - серверная база хостинга, доступная Worker через env.DB.

```javascript
await env.DB
  .prepare('INSERT OR IGNORE INTO saved_advice (id, source, text) VALUES (?, ?, ?)')
  .bind(id, source, text)
  .run()
```

Prepare готовит SQL-выражение. Вопросительные знаки являются placeholders - местами для значений. Bind передаёт значения отдельно, run выполняет. Это не склейка пользовательского текста с синтаксисом команды.

Идентификатор вычисляется SHA-256 из нормализованных source и text. Hash - детерминированный отпечаток байтов: одинаковый вход даёт одинаковый результат. Это не шифрование: сам текст хранится отдельной колонкой.

Primary key - уникальный основной ключ строки. Insert or ignore при уже существующем id не создаёт второй экземпляр записи. Поэтому повтор POST после перемонтирования кнопки не увеличивает копилку дубликатом.

Миграция - версия изменения SQL-схемы. Файл drizzle/0000_saved_advice.sql создаёт таблицу, журнал сообщает инструменту её имя и порядок. Наличие папки drizzle не означает использование ORM: в коде запросы прямые. ORM - дополнительный слой, представляющий SQL-данные средствами языка программы; в этой реализации такого слоя нет.

Локально схема применяется при настройке сервера до HTTP-запросов. На хостинге применяется миграцией. Обработчик GET не создаёт таблицу заново. Локальная синхронная обёртка предоставляет интерфейс, похожий на D1, чтобы общий обработчик не дублировался.

## 19. Проверка ошибок и пустоты

Ошибка чтения относится к query, ошибка сохранения к mutation. Их нужно показать отдельно.

Для ошибки сохранения блокирую /api/saved на главной и нажимаю ещё доступную кнопку. Получаю сообщение, снимаю блокировку и повторяю. Если включить общий Offline, библиотека может приостановить операцию до восстановления сети; для ожидаемой ошибки удобнее блокировка конкретного запроса.

Для ошибки чтения нужно действительно выполнить новый GET. Со свежим кешем переход может вообще не обратиться к сети, и блокировка не проявится. Полное открытие страницы с блокировкой позволяет подготовить этот сценарий, затем её снимаем и нажимаем «Повторить».

Для пустоты можно через Local Overrides подменить успешный GET на []. Это учебная подмена браузером, не удаление реальных записей. После проверки нужно отключить её. Пустая копилка и пустой результат фильтра имеют разные сообщения.

Если запись видна под другим фильтром, это не ошибка сохранения. Сначала проверь выбранный source. Если сохранил на localhost и не увидел на хостинге, проверь, что обращаешься к той же базе: они раздельные.

## 20. Вопросы преподавателя и готовые короткие ответы

### Почему Zustand?

Для одного общего фильтра достаточно небольшого store. Задание допускает его. Мы не добавляем много служебного кода ради одной строки состояния.

### Почему серверные ответы не в store?

Их уже хранит QueryClient. Дублирование потребовало бы согласовывать массивы после каждой загрузки и записи, чего мы избегаем.

### Зачем ещё Axios?

TanStack Query организует получение и кеш, но queryFn всё равно нужна функция фактического HTTP. Мы сохранили общий Axios с настройками и перехватчиками.

### Сохраняется ли всё после F5?

Нет. Кеш памяти и фильтр создаются заново. Серверные записи остаются в базе и читаются новым GET. Это разные виды сохранения.

### Почему две страницы имеют один фильтр?

Store создан выше их жизненного цикла на уровне модуля. Обе страницы подписаны на одну строку, а не имеют два независимых useState.

### Почему ключ вопроса не меняется от каждого символа?

Query получает submittedQuestion, не черновик. Изменение происходит после отправки формы.

### Что происходит при unknown route?

Обычный путь страницы получает HTML fallback, затем Router показывает запасной экран. Отсутствующий файл и API обрабатываются отдельными серверными 404.

### Почему после записи нет мгновенной синхронизации у всех посетителей?

WebSocket и общий механизм push-уведомлений не реализованы. У каждого браузера свой кеш. Наше действие инвалидирует соответствующий кеш текущего клиента.

### Есть ли здесь авторизация пользователей?

Личных аккаунтов копилки нет. Приватный доступ владельца к сайту обеспечивает хостинг отдельно. Проверка Origin не заменяет полноценный вход пользователя.

### Как проверить работу без гарантии внешнего API?

Логику состояний проверяют управляемыми ответами, копилку отдельно реальными запросами к своему серверу. Для заявления об успешном живом ответе совы нужна отдельная настоящая проверка источника. Нельзя выдать тестовый текст за генерацию API.

## 21. Завершение защиты и памятка

> В работе один общий store, несколько согласованных потребителей и две страницы с клиентской навигацией. Все браузерные API-запросы выполняются query/mutation через общий Axios. Есть кеш, загрузка, ошибка, повтор и пустота. Сохранение действительно меняет серверные данные, после успеха инвалидируется связанный список. Ответы не копируются в Zustand.

Для защиты на 3 минуты: фильтр между страницами, store, query-кеш, mutation с POST, инвалидация и новый GET. Для полной защиты добавь ошибку, пустоту, прямую ссылку, историю браузера и объяснение SQL.

Не заменяй смысл термином. Если забыл слово «инвалидация», скажи: «После записи я помечаю старый список неактуальным, и при открытии копилки он загружается снова». Затем назови соответствующий метод.

## 23. Что было проверено и чего нельзя обещать

При реализации проверялись автоматические сценарии компонентов, общий фильтр, отправка и повтор старого вопроса, состояния query/mutation, кеш, инвалидация и история. Это не является визуальной проверкой настоящим браузером.

На опубликованном сайте подтверждены SQL-таблица, чтение копилки, запись и защита от дубликата. Оставлена явно подписанная проверочная запись о сохранении. Она не является ответом внешней модели.

При последней живой проверке ответ совы завершился 502, а обращение к Канье из проверочного окружения получило 403. Это историческое ограничение проверки, а не утверждение о состоянии сервисов в момент чтения. Перед защитой проверь их заново и не выдавай контрольные данные за успешный внешний ответ.

Копилка не проверяет криптографически, действительно ли присланный клиентом текст произнёс указанный источник. У неё нет аккаунтов, пагинации, удаления и постоянной межклиентской синхронизации. Эти функции не следует приписывать текущему коду.

Нажал «В копилку»
