# Лабораторная работа 6: подробный гайд по защите

Дата снимка: 27 октября 2026 года. Ветка: `lab6-state`. Этот документ относится к шестой лабораторной и текущему рабочему коду. Гайды в `docs/lab5` описывают предыдущую версию и не заменяют этот разбор.

Второй документ: [полный построчный разбор](02-line-by-line.md). Здесь разбираем смысл работы, демонстрацию и вопросы преподавателя. Во втором документе последовательно объясняется весь собственный код, включая сервер, SQL, стили и сборку.

## 1. Главная мысль шестой лабы

Пятая работа была про реальные HTTP-запросы и состояния загрузки. Шестая - про разделение состояния приложения, страницы и управление серверными данными через специальную библиотеку.

У нас три разных места хранения:

1. **Локальное состояние React**: текст поля, ошибка ввода, последний отправленный вопрос. Оно нужно странице вопроса.
2. **Zustand**: выбранный фильтр `all`, `owl` или `kanye`. Он нужен переключателю и обеим страницам.
3. **TanStack Query**: результаты запросов, ошибки, признаки загрузки и кеш серверных данных.

Дополнительно серверная база хранит копилку постоянно. Это не четвёртая копия клиентского массива: база является источником данных, а браузерный кеш временно хранит результат её чтения.

На защите нельзя сводить работу к фразе «я поставил три библиотеки». Нужно объяснить, какое состояние досталось каждой и почему.

## 2. Что пользователь делает на сайте

На `/` пользователь задаёт вопрос. Сова отвечает по смыслу через серверный маршрут, Канье возвращает случайную английскую цитату. Под каждым ответом можно нажать «В копилку».

На `/saved` пользователь видит сохранённые тексты. Копилка общая для посетителей сайта, без аккаунтов. Это не личное избранное конкретного пользователя.

Переключатель «Кого слушаем» фильтрует карточки и на главной, и в копилке. Перешёл между страницами - выбор остался. Полностью перезагрузил браузерную страницу - фильтр вернулся к `all`. Задание не требует сохранять этот выбор после полной перезагрузки.

Кнопка сохранения делает реальный POST. Во время операции повтор недоступен, при ошибке можно нажать снова, после успеха связанные данные помечаются устаревшими. На странице копилки появляется актуальный список без ручного обновления документа.

Удаления, редактирования, аккаунтов, тегов и поиска нет. Одного действия создания записи достаточно для пункта mutation, а лишние операции не нужны для текущего объёма.

## 6. Zustand: разобрать так, чтобы объяснить без терминов

Store создаётся вызовом `create` вне React-компонентов. Функция возвращает хук `useFilter`.

Содержимое store небольшое:

```javascript
{
  source: 'all',
  setSource: source => set({ source }),
}
```

`SourceFilter` читает значение и действие. При выборе option обработчик получает строку из select и вызывает `setSource`. Store обновляется. Подписанные компоненты получают новый выбранный источник.

`AdvicePage` фильтрует массив карточек до `map`. `SavedPage` фильтрует массив полученных записей. Меняется отображение, а не содержимое базы.

Смена фильтра не запускает новый запрос. Фильтрация клиентская, данные источников уже запрашиваются независимо. Если выбран только Канье, это не означает, что запрос совы вообще не был выполнен.

Store не находится внутри страницы, поэтому переключение маршрута не создаёт его заново. При полной перезагрузке загружаются модули нового документа, и исходное значение снова `all`. Механизма persist в проекте нет.

## 7. Router: два разных вида перехода

При переходе через NavLink Router обновляет адрес и выбранный компонент. Браузер не загружает новый HTML-документ целиком. Общая оболочка App, store и QueryClient продолжают жить.

При прямом открытии `/saved` браузер сначала обращается к серверу именно за этим адресом. Сервер должен вернуть HTML приложения. Уже затем React Router выберет SavedPage. Одного BrowserRouter без серверного fallback было бы недостаточно.

Наш Worker сначала обрабатывает API, затем ищет статический файл, а для пути без точки в последнем сегменте использует index.html. Поэтому обычные страницы вроде `/saved` и `/unknown` получают оболочку. Неизвестный путь страницы попадёт в Route `*`.

Неизвестный `/api/...` получает JSON 404. Несуществующий файл вроде `/missing.js` получает HTTP 404. Не надо отдавать HTML вместо любого JavaScript-файла: это вызвало бы ошибку загрузки скрипта.

Граница текущего простого fallback: адрес, последний сегмент которого содержит точку, считается похожим на файл. Не утверждай, что обработчик универсально поддерживает любые будущие схемы URL.

## 8. TanStack Query: кто выполняет какую работу

Axios остаётся транспортом: отправляет HTTP, применяет таймаут и перехватчики, отдаёт разобранный JSON.

TanStack Query организует вызов API-функции, состояние запроса, кеш, повторное обращение и инвалидацию. Функция `getSaved` не знает о JSX, а SavedPage не пишет собственный `fetch`.

`QueryClient` создаётся один раз в `src/api/queryClient.js`. В `main.jsx` QueryClientProvider делает его доступным компонентам. Создавать новый QueryClient внутри рендера App было бы ошибкой: кеш терял бы нужную стабильность.

У query есть ключ и функция. Ключ определяет, к каким данным относится запись кеша. Функция должна вернуть Promise с данными или выбросить ошибку. Пустой массив является допустимыми данными. Объект ошибки не следует возвращать как будто это успешный массив.

## 9. Наши ключи кеша

| Ключ | Какие данные обозначает |
| --- | --- |
| `['advice', 'owl', question]` | Ответ совы для конкретного отправленного вопроса |
| `['advice', 'kanye']` | Последняя загруженная случайная цитата |
| `['saved']` | Общий список копилки |

Вопрос включён в ключ совы, потому что меняет содержание запрашиваемого ответа. В ключе Канье его нет: этот источник вопрос не использует. Фильтра в ключе копилки нет, потому что сервер отдаёт общий список, а фильтр применяется уже в компоненте.

При новом вопросе меняется ключ совы, и query выбирает соответствующую запись кеша или загружает её. Если такой вопрос уже был и его данные ещё свежие, возможен ответ из кеша. Для одинакового текущего вопроса обработчик явно вызывает reload, чтобы пользователь получил обновление.

Query key не является URL, SQL-ключом или React key. Эти идентификаторы решают разные задачи.

## 10. Свежесть, хранение и инвалидация

В нашем QueryClient задан `staleTime: 60000`, то есть 60 секунд свежести. Пока данные свежие, быстрый уход и возврат на страницу не требует обычного повторного запроса при монтировании.

Это не таймер удаления и не периодический опрос. Через 60 секунд данные становятся устаревшими, но из одного этого не следует немедленный HTTP-запрос ровно на 60001-й миллисекунде. Повтор зависит от события, например повторного монтирования устаревшего query или ручного refetch.

`gcTime` мы не переопределяем. Для неактивного клиентского query действует стандартное время удаления около 5 минут. Оно отсчитывается, когда у query нет активных наблюдателей, а не просто с момента первого успешного ответа.

`refetchOnWindowFocus: false` отключает обычное обновление при возврате фокуса. `retry: false` отключает автоматические повторные попытки после ошибки. Ручные кнопки повтора продолжают работать. Остальные настройки, например поведение при восстановлении соединения, отдельно не переопределены.

Инвалидация сообщает, что связанные данные больше нельзя считать актуальными. Для активного списка возможен немедленный повторный запрос. Если копилка сейчас не открыта, её кеш помечается устаревшим, а запрос придёт при следующем открытии.

В нашей навигации сохранение происходит на главной, а копилка - другой маршрут. Поэтому после сохранения нормально не увидеть GET `/api/saved` до перехода в копилку. Отсутствие мгновенного GET в этом сценарии не означает, что `invalidateQueries` не сработал.

Дополнительные определения: [настройки по умолчанию TanStack Query](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults).

## 11. Полный путь получения ответа

```text
Открытие AdvicePage или изменение submittedQuestion
-> useAdvice(question)
-> useQuery выбирает queryKey
-> при необходимости вызывает queryFn
-> getOwl(signal, question) или getKanye(signal)
-> общий Axios instance
-> HTTP
-> API-функция проверяет JSON и возвращает массив
-> TanStack Query обновляет кеш и состояние query
-> useAdvice строит представление results
-> AdvicePage фильтрует карточки
-> AdviceResult показывает текст, ожидание, пустоту или ошибку
```

`results` здесь вычисляется при рендере. Он не сохраняется вторым массивом в useState и не создаёт второй самостоятельный кеш. Локальные метаданные карточки соединяются с текущими свойствами query для удобства отображения.

Для совы есть ещё серверный участок: `/api/owl -> handleOwl -> внешний API -> { advice }`. Секрет применяется только там. Серверный fetch является внутренней реализацией backend и не является обходом query-хуков React.

## 12. Отправка формы и повтор

В поле хранится `question`, а query получает `submittedQuestion`. Поэтому печатание каждого символа не отправляет запрос. Смена query key происходит после корректной отправки формы.

Обработчик:

1. Отменяет стандартную отправку формы.
2. Проверяет, не идёт ли загрузка.
3. Обрезает пробелы и отклоняет пустоту.
4. Очищает сообщение ошибки ввода.
5. Если вопрос совпал с последним отправленным, вызывает reload обоих источников.
6. Если вопрос новый, сохраняет его в submittedQuestion. Это меняет ключ совы. Отдельно обновляет Канье, чей ключ от вопроса не зависит.

Нельзя после setSubmittedQuestion сразу вызывать refetch старого query совы в надежде, что его замыкание уже изменилось. Setter запланировал новый рендер, но текущая функция ещё видит старое значение. Поэтому новый вопрос обрабатывается изменением ключа.

Кнопка «Повторить» в конкретной карточке вызывает refetch только соответствующего query. Если пользователь менял черновик без отправки, query совы всё ещё связан с submittedQuestion, и повтор относится к прежнему вопросу.

При уходе с главной её локальные состояния размонтируются. При возвращении поле и submittedQuestion начинаются заново. Общий фильтр и кеш продолжают жить, но это не означает сохранение черновика формы между страницами.

## 13. Полный путь сохранения

```text
Кнопка «В копилку»
-> handleSave проверяет isPending и isSuccess
-> save.mutate({ source, text })
-> mutationFn: saveAdvice
-> общий http.post('/api/saved', advice)
-> handleSaved проверяет JSON
-> нормализация текста и вычисление id
-> INSERT OR IGNORE с параметрами
-> сервер возвращает { id, source, text }
-> onSuccess инвалидирует ['saved']
-> кнопка показывает «Сохранено»
-> при открытии копилки query получает актуальный список
```

Состояние mutation не равно состоянию query. Первое относится к действию записи, второе к чтению данных. Успех сохранения не означает, что копилку надо вручную присвоить в Zustand.

Наш onSuccess возвращает Promise от invalidateQueries. Библиотека учитывает его завершение при окончании mutation. Это полезно понимать, если в другом интерфейсе список окажется активным и начнёт обновляться сразу. [Связь mutation и инвалидации](https://tanstack.com/query/latest/docs/framework/react/guides/invalidations-from-mutations).

## 14. Сервер и защита от повторной записи

Запись содержит только `id`, `source`, `text`. Источник обязан быть owl или kanye, текст строкой длиной до 4000 после обрезки краёв. Пустоту сервер отклоняет, даже если клиент обошли.

Идентификатор вычисляется из нормализованной строки `source:text` через SHA-256. Одинаковый источник и одинаковый нормализованный текст дают одинаковый id. В SQL id является PRIMARY KEY, а INSERT OR IGNORE не создаёт вторую строку с тем же ключом.

Это защищает не только от повторного нажатия текущей кнопки, но и от повторного POST после перемонтирования компонента или сетевой неопределённости. При повторном сохранении уже существующего текста сервер возвращает нормальный успешный результат. Он не создаёт новую запись ради демонстрации.

Хеширование здесь не является шифрованием и не скрывает текст. Текст хранится отдельно открытым полем. Хеш не подтверждает, что содержание действительно произнёс внешний API: маршрут принимает данные от клиента. Полноценной проверки происхождения и аккаунтов в учебном проекте нет.

SQL использует placeholders `?` и bind. Текст пользователя не склеивается с синтаксисом SQL. GET выбирает три поля и сортирует по rowid по убыванию. Rowid служит внутренним порядком вставки, а не отдельным публичным полем даты.

## 15. Локальная база и хостинг

Локально Vite работает в Node. openLocalDatabase создаёт папку `.data`, открывает файл SQLite и применяет начальный CREATE TABLE IF NOT EXISTS. Это происходит при настройке сервера, до обработки запросов.

Небольшая обёртка приводит синхронные методы SQLite к тому виду, который ожидает общий обработчик D1: prepare, all, bind и run. Await допускает и готовое обычное значение, поэтому общий обработчик работает с локальной обёрткой и настоящим асинхронным D1.

На хостинге Worker получает env.DB. Схема применяется механизмом миграций из папки drizzle. Во время HTTP-запроса таблица не создаётся. Журнал `_journal.json` сообщает порядок и имя SQL-миграции. В проекте нет импортов Drizzle ORM: наличие папки с миграцией не означает использование ORM в обработчиках.

SQLite-файл на ноутбуке и D1 хостинга - разные базы. Запись на localhost не должна автоматически появляться в опубликованной копилке. Полная перезагрузка браузера не удаляет серверные записи.

Для локальной версии проект документирован под Node.js 24, потому что используется встроенный node:sqlite. Наличие более старой версии, достаточной только для прежнего Vite-проекта, ещё не гарантирует наличие нужного SQLite API.

## 18. Подробная репетиция состояний

### Загрузка query

Временно замедли соединение в Network и перезагрузи главную. До получения ответов видны сообщения ожидания, сова и disabled формы. На копилке первая загрузка имеет свой текст. После демонстрации верни обычное соединение.

Смена поз каждые 2800 мс не заставляет сеть ждать. Если источник ответил быстро, кадры могут не успеть смениться. Это нормальное поведение.

### Ошибка чтения

Заблокируй адрес копилки в DevTools и полностью открой страницу заново, чтобы не использовать свежий кеш. После неудачного GET покажи сообщение и кнопку. Сними блокировку и нажми «Повторить».

Если просто перейти на страницу со свежим кешем, HTTP может не начаться и сетевая блокировка не проявится. Это не провал проверки ошибки, а проявление кеширования. Для проверки нужно действительно инициировать новый запрос.

### Ошибка записи

Нужен доступный несохранённый текст. Заблокируй `/api/saved`, оставаясь на главной, и нажми «В копилку». Этот сценарий проверяет POST. Когда ошибка показана, сними блокировку и нажми снова. Отклонённая mutation автоматически не повторяется: retry:false.

Если включить общий браузерный Offline, TanStack Query может поставить операцию на паузу до восстановления сети. Это не тот же сценарий, что полученная серверная ошибка. Для предсказуемой демонстрации ошибки удобнее блокировка отдельного запроса.

### Пустая копилка

При использовании Chrome или Edge открой успешный GET `/api/saved`, выбери подмену содержимого ответа и замени тело на `[]`. После сохранения подмены перезагрузи страницу копилки, чтобы новый QueryClient действительно получил это тело.

Это контролируемая проверка редкого состояния. Скажи преподавателю, что тело ответа подменено локально для демонстрации. Настоящие серверные записи не удаляются. После проверки отключи Overrides и снова загрузи обычные данные. [Настройка Local Overrides](https://developer.chrome.com/docs/devtools/overrides).

### Пустой результат фильтра

Если в копилке есть только сова, выбери Канье. Сообщение будет «По этому фильтру советов пока нет». Сама копилка не пуста. Сравни это с `[]`: тогда показывается приглашение сохранить первый совет.

### Ошибка формата

Для GET копилки подмени JSON на объект вместо массива либо массив с числом вместо text. API-функция должна выбросить понятную ошибку формата. Это проверка структуры данных, а не обязательно HTTP 500.

### Повтор старого вопроса

Отправь вопрос и добейся ошибки карточки совы. Измени черновик без отправки. Нажми повтор совы. В POST должен оставаться submittedQuestion. Возвращаться на другую страницу во время этой проверки не нужно: локальное состояние страницы при уходе сбрасывается.

### Проверка дубликата

Сохрани текст. Затем после нового монтирования или повторного получения того же текста можно отправить его снова. Сервер вернёт успех, но GET не должен содержать две записи с тем же id. Disabled текущей кнопки и серверный PRIMARY KEY решают разные уровни задачи.

### После репетиции

Убери Overrides, блокировки и замедление. Не коммить локальную папку подмен, SQLite-файл, журналы запросов или ключ. Не удаляй серверную копилку ради скриншота пустого состояния.

## 19. Возможные вопросы преподавателя

### 1. Какая главная тема шестой работы?

Управление состоянием и серверными данными, разделение ответственности библиотек и навигация. В нашем коде это Zustand, TanStack Query и React Router. Реальные HTTP-запросы пятой работы остаются, но организованы иначе.

### 2. Почему выбрал Zustand, а не Redux Toolkit?

Для единственного фильтра достаточно небольшого store с одним действием. Задание допускает оба варианта. Мы не сравниваем их как всегда хороший и всегда плохой инструменты, а выбираем меньший объём кода для своей задачи.

### 3. Почему вместе с Zustand нужна ещё TanStack Query?

Это прямое условие уровня 5 для варианта с Zustand. Кроме того, фильтр и серверные ответы имеют разную природу. Store отвечает за выбор пользователя, Query за загрузку, кеш и состояние сети.

### 4. Какие минимум два компонента используют общее состояние?

SourceFilter читает source и меняет его, AdvicePage по нему скрывает карточки, SavedPage фильтрует записи. Компоненты согласованно используют один и тот же store, хотя страницы не показаны одновременно.

### 5. Почему store не пересоздаётся?

Вызов create находится на уровне модуля. При обычных рендерах компоненты только вызывают уже созданный хук useFilter с селектором. Внутри App нового create нет.

### 6. Что такое селектор Zustand?

Функция, которая выбирает нужное значение из состояния. `state => state.source` выбирает строку, другой селектор выбирает setSource. Компонент подписывается на используемый результат, а не обязан читать весь объект целиком.

### 7. Что делает set в store?

Обновляет состояние Zustand. `set({ source })` меняет соответствующее поле с обычным поверхностным объединением, сохраняя действие setSource. Это не React-setter массива результатов.

### 8. Почему в Zustand нет ответов API?

Они уже находятся в кеше TanStack Query. Дополнительный массив в store пришлось бы синхронизировать после каждой загрузки и mutation. Задание прямо просит не дублировать API-ответы в клиентском хранилище.

### 9. Почему source не хранится просто в App через useState?

Так тоже можно было бы построить маленький сайт через props, но лабораторная требует внешний store. Мы выбрали значение, которое действительно нужно нескольким компонентам и маршрутам.

### 10. После F5 фильтр пропадает, это ошибка?

Нет, в задании сохранение после полной перезагрузки не требуется. Persist или localStorage для фильтра не подключены. Между клиентскими переходами значение остаётся.

### 11. При смене фильтра запросы отменяются?

Нет. Фильтр управляет видимыми карточками, а обе query-функции уже подключены к странице. Скрытие результата в JSX не равно отключению useQuery.

### 12. Почему фильтра нет в queryKey копилки?

GET возвращает общий массив, а filter выполняется в браузере. У разных выбранных источников одна серверная выборка. Если бы сервер принимал параметр фильтра и отдавал разные наборы, ключ следовало бы расширить.

### 13. Что такое BrowserRouter?

Router, который связывает компоненты с обычным адресом браузера и его историей. Он оборачивает App в main.jsx. Это не отдельный HTTP-сервер.

### 14. Что делает Routes?

Сопоставляет текущий адрес с объявленными Route и выбирает соответствующий элемент. У нас главная, копилка и запасной маршрут `*`.

### 15. Зачем NavLink вместо обычного a?

Он выполняет внутреннюю навигацию Router без полной загрузки документа и позволяет выделить активный пункт. Внешние ссылки при этом могут оставаться обычными ссылками.

### 16. Зачем end у ссылки на корень?

Чтобы корневая ссылка считалась активной при точном совпадении с `/`, не обозначая каждую вложенную страницу как главную. В нашем меню это подчёркивает текущий раздел.

### 17. Что сохраняется при переходе, а что нет?

Store и QueryClient остаются в общей области приложения. Локальные state размонтированной страницы теряются. Поэтому фильтр сохраняется, но черновик вопроса после ухода с главной не обещан.

### 18. Почему прямое открытие страницы сложнее перехода через ссылку?

При прямом открытии сервер сначала получает `/saved`. Если он вернёт 404, Router не загрузится. Нужен HTML fallback для страницы, который реализован в Worker.

### 19. Что будет с неизвестным адресом?

Для обычного пути без расширения сервер отдаст оболочку, и Route `*` покажет сообщение. Неизвестный API или отсутствующий файл обработается серверным 404. Это разные случаи.

### 20. У неизвестной страницы HTTP-статус 404?

Не обязательно. В нашем клиентском fallback HTML возвращается успешно, а сообщение об отсутствии страницы выбирает Router. Настоящий серверный 404 предусмотрен для отсутствующих файлов и API. Не приписывай SPA-маршруту серверный статус, которого код не выставляет.

### 21. Что делает QueryClientProvider?

Даёт дочерним компонентам доступ к одному QueryClient через контекст. Без нужного провайдера query-хуки не получат клиент приложения. Провайдер сам не является таблицей SQL.

### 22. Где создаётся QueryClient?

В src/api/queryClient.js на уровне модуля. Main импортирует готовый объект и передаёт провайдеру. Создание внутри каждого рендера привело бы к нестабильной организации кеша.

### 23. Чем query отличается от mutation?

Query описывает получение данных с ключом и кешем. Mutation описывает действие записи или изменения. В проекте чтение ответов и списка - queries, сохранение новой записи - mutation.

### 24. Почему ответ совы через POST оформлен query?

HTTP-метод и назначение query-библиотеки не являются одним правилом. Наш POST передаёт вопрос для получения ответа и не создаёт запись копилки. Для реального изменения хранимых данных есть отдельная mutation `/api/saved`. Сама операция генерации при этом расходует внешний ресурс, поэтому повторные обращения выполняются осознанно.

### 25. Что такое queryFn?

Функция получения данных конкретного query. Она получает контекст, например signal, и возвращает Promise результата. В useAdvice она вызывает обычную API-функцию, не строит JSX.

### 26. Что такое queryKey?

Идентификатор данных в кеше. Один и тот же ключ обозначает одну логическую запись query. В ключ совы включён вопрос, потому что он влияет на ответ.

### 27. Почему вопрос нельзя исключить из ключа совы?

Тогда разные вопросы имели бы один идентификатор кеша, что смешивало бы результаты. Зависимое от запроса значение должно быть отражено в ключе, если оно определяет данные.

### 28. Почему нет вопроса у Канье?

Этот API возвращает случайную цитату и не читает пользовательскую ситуацию. Включать вопрос в его ключ не нужно. При отправке формы мы отдельно вызываем его refetch.

### 29. Что такое isPending у query?

У query ещё нет успешно полученных данных для соответствующего состояния. Обычно это первая загрузка, но без сети выполнение может быть на паузе. Нельзя говорить, что isPending всегда означает активную отправку байтов.

### 30. Что такое isFetching?

Сейчас выполняется загрузка, включая обновление уже известных данных. Поэтому он может быть true одновременно с наличием прежнего успешного результата. Наш UI отдельно учитывает такой случай.

### 31. Где хранится status loading/success/empty/error?

В useAdvice это вычисляемое представление для прежней карточки, собранное из query-состояний. Отдельного useState с этими статусами нет. Empty определяется по длине успешного массива, а не является стандартным статусом TanStack Query.

### 32. Показываем ли старый ответ при повторной загрузке?

На главной useAdvice специально передаёт пустой массив во время isFetching, чтобы карточка показала ожидание. Кеш при этом не обязательно очищается. В копилке прежние записи могут оставаться видимыми вместе с сообщением обновления.

### 33. Ошибка фонового обновления обязательно уничтожает старые данные?

Нет. Query может сохранить прежние данные. SavedPage строит items из доступных data и отдельно показывает ошибку. На главной наш преобразователь скрывает данные при isError. Это решения UI, а не единое обязательное правило библиотеки.

### 34. Что делает refetch?

Просит выполнить запрос текущего query снова. Это используется для ручного повтора, в том числе при свежих данных. Он не меняет сам по себе вопрос в queryKey.

### 35. Зачем два состояния вопроса?

Question - черновик. SubmittedQuestion - последний корректно отправленный текст, определяющий query. Печатание не вызывает запрос на каждый символ, а повтор карточки не захватывает неотправленный черновик.

### 36. Почему при новом вопросе нет ручного refetch совы?

Смена submittedQuestion создаёт новый ключ. useQuery сам выбирает или загружает нужные данные. Немедленный вызов старого refetch в том же обработчике мог бы относиться к прежнему значению.

### 37. Почему одинаковый отправленный вопрос всё же обновляется?

Состояние с той же строкой не дало бы нового ключа. Поэтому обработчик проверяет совпадение и явно вызывает reload обоих источников. Это отдельное пользовательское действие получения новых ответов.

### 38. Что стало с AbortController пятой работы?

Собственный контроллер сетевого эффекта удалён. Query-функция получает signal от TanStack Query и передаёт его в Axios. Библиотека управляет жизненным циклом query, а API-модуль поддерживает отмену.

### 39. Значит ли отмена браузерного запроса гарантированную остановку внешней генерации?

Нет. Клиентская отмена и выполнение серверного внешнего запроса - разные уровни. Серверный обработчик имеет свой таймаут. Нельзя обещать прекращение всей удалённой работы и списания ресурсов только на основании сигнала Axios.

### 40. Почему useEffect остался в Owl?

Задание заменяет старую организацию API-запросов через эффект. Интервал анимации является другой внешней системой и по-прежнему требует настройки и очистки. Сетевого useEffect в useAdvice больше нет.

### 41. Нужен ли теперь useCallback для reload?

В текущем варианте reload не является зависимостью сетевого эффекта. Он вызывается обработчиками, поэтому прежняя причина useCallback исчезла. Добавлять мемоизацию автоматически ко всем функциям не требуется.

### 42. Как долго кеш свежий?

В нашей конфигурации 60 секунд. Это влияет на обычные повторные обращения к тем же данным. После инвалидации свежесть отменяется раньше.

### 43. Через минуту будет автоматический запрос?

Не только из-за истечения staleTime. Данные станут устаревшими. Нужен соответствующий триггер, например монтирование, восстановление соединения по настройкам или ручной refetch. RefetchInterval мы не задаём.

### 44. Что такое gcTime?

Время, после которого неактивные query могут быть удалены из памяти. Мы оставили клиентское значение по умолчанию около 5 минут. Это не те же 60 секунд свежести.

### 45. Что значит активный query?

На него есть активный наблюдатель, например смонтированный useQuery страницы. После ухода со страницы query может остаться в кеше, но стать неактивным. Запись не обязана немедленно удаляться.

### 46. Почему нет автоматических повторов после ошибки?

В defaultOptions установлен retry:false для queries и mutations. Мы хотим явное сообщение и управляемый ручной повтор. Это не отключает кнопки refetch или повторного mutate.

### 47. Почему при переключении окна нет нового запроса?

RefetchOnWindowFocus отключён. Это уменьшает неожиданные обновления случайной цитаты и генерации. Другие причины нового запроса, включая инвалидацию и переход на устаревшие данные, остаются.

### 48. Перезагрузка сохраняет query-кеш?

Нет, наш QueryClient живёт в памяти документа и не использует persistence. Серверные записи сохраняются в базе, но их новый GET после F5 создаёт новый кеш браузера.

### 49. Чем HTTP-кеш отличается от query-кеша?

Первый относится к сетевому протоколу и браузерным HTTP-правилам. Второй управляется JavaScript-библиотекой по queryKey. Cache-Control:no-store сервера не запрещает TanStack Query хранить полученный результат в своей памяти.

### 50. Почему в Network нет GET при возвращении в копилку?

Если кеш ещё свежий и не инвалидирован, библиотека может использовать его. Это ожидаемая демонстрация работы кеша, а не отсутствие HTTP вообще: первоначальный запрос уже был.

### 51. Что конкретно делает invalidateQueries?

Находит связанные query по ключу, помечает их устаревшими и при обычных условиях обновляет активные. Неактивная копилка загрузится при последующем открытии. Эта операция не выполняет INSERT и не удаляет SQL-таблицу.

### 52. Почему после сохранения не всегда немедленно виден GET?

Сохраняем на главной, SavedPage в этот момент не смонтирована. Инвалидация помечает её кеш, а следующий GET появляется при переходе. В коде не задано обязательное немедленное обновление всех неактивных query.

### 53. Где именно mutation?

В SaveButton.jsx: useMutation с mutationFn:saveAdvice. По нажатию вызывается mutate с source и text. Возвращаемый объект даёт isPending, isError и isSuccess для интерфейса.

### 54. Почему mutation не запускается при рендере?

В useMutation передана ссылка на saveAdvice, а в кнопку ссылка на handleSave. Само действие запускается вызовом mutate в обработчике. Мы не записываем mutate(...) прямо при построении JSX.

### 55. Как предотвращается двойная отправка?

Настоящий button получает disabled при isPending, обработчик тоже проверяет статус. После успеха кнопка недоступна в текущем экземпляре. На сервере одинаковая нормализованная запись дополнительно защищена стабильным id и PRIMARY KEY.

### 56. Что происходит при ошибке mutation?

Объект useMutation становится ошибочным, показывается сообщение, кнопку снова можно нажать. OnSuccess и его инвалидация при обычной ошибке POST не выполняются. Пользователь запускает новую попытку явно.

### 57. Почему onSuccess возвращает Promise?

Стрелочная функция без фигурных скобок возвращает результат invalidateQueries. TanStack Query может дождаться его завершения, прежде чем считать обработку успеха полностью законченной. Это особенно заметно при активном связанном списке.

### 58. Почему мы не делаем optimistic update?

Задание требует инвалидацию, и для маленькой копилки проще дождаться сервера и затем актуализировать список. Предварительная вставка потребовала бы отката при ошибке и дополнительной логики. Она не нужна для текущей цели.

### 59. Почему нет ручного массива saved в useState?

Тогда пришлось бы вручную согласовывать его с query-кешем после каждой записи и перехода. В SavedPage список берётся из saved.data. Filter создаёт отображаемый массив, но не хранит вторую независимую копию состояния.

### 60. Состояние «Сохранено» переживёт любой переход?

Не гарантируется. Оно относится к экземпляру кнопки mutation, который может размонтироваться при уходе или загрузке. Серверная запись остаётся. Если кнопку создать снова и повторить сохранение, база не создаст дубликат.

### 61. Почему React key текста включает сам текст?

Новый ответ в том же источнике должен получить новый экземпляр блока с кнопкой и чистым состоянием сохранения. id источника остаётся тем же, а текст отличает ответ. Это стабильный ключ для данного текста, а не Math.random при каждом рендере.

### 62. Копилка личная?

Нет. На сервере одна общая таблица без userId. Пользовательские аккаунты и персональные коллекции не реализованы. Приватность доступа ко всему сайту на хостинге не превращает каждую запись в отдельное личное избранное.

### 63. Какие поля у записи?

Id, source и text. Время, вопрос, автор-пользователь и теги не добавлялись. Source обозначает owl или kanye, а не личность посетителя.

### 64. Почему используем SHA-256?

Для детерминированного идентификатора одинакового источника и текста. Это позволяет серверу распознать повторную запись без отдельного поиска по всем строкам и без случайного нового id для каждого POST.

### 65. Это шифрование текста?

Нет. Хеширование создаёт отпечаток, а текст хранится отдельным полем. Из наличия хеша не следует конфиденциальность данных. Авторизация и шифрование здесь не реализованы самим этим вычислением.

### 66. Как байты становятся строковым id?

TextEncoder переводит source:text в UTF-8-байты. Digest возвращает буфер из 32 байтов. Каждый байт переводится в шестнадцатеричную строку длиной 2, затем строки соединяются в 64 символа.

### 67. Что делает INSERT OR IGNORE?

Пытается вставить строку. При конфликте уже существующего первичного ключа новая строка не создаётся. В нашей схеме нужный конфликт соответствует повторному сохранению того же нормализованного текста.

### 68. Почему POST возвращает 200, а не обязательно 201?

Reply по умолчанию использует 200, и действие может вернуть уже существующую запись без новой вставки. Код не различает эти случаи отдельным статусом. Успех mutation не обязан означать, что число строк всегда увеличилось.

### 69. Зачем bind и вопросительные знаки в SQL?

Значения передаются параметрами, отдельно от SQL-структуры. Апостроф внутри текста не становится частью команды. Это лучше, чем склеивать пользовательский текст прямо с INSERT.

### 70. Что такое rowid в SELECT?

Внутренний идентификатор обычной SQLite-таблицы. ORDER BY rowid DESC показывает более поздние вставки раньше. Наш публичный id является текстовым SHA-256, а rowid не выдаётся отдельным полем API.

### 71. Где база локально?

В .data/saved.sqlite. Папка игнорируется Git и создаётся при настройке Vite-сервера. После остановки и нового запуска файл остаётся, если его специально не удалять.

### 72. Где база на опубликованном сайте?

В D1, доступном Worker через env.DB. Это отдельная база от файла на ноутбуке. Сайту не нужен доступ к диску твоего компьютера для чтения опубликованной копилки.

### 73. Что такое миграция?

Версионированное описание изменения схемы. Наша начальная SQL-миграция создаёт таблицу с ограничениями. При будущих изменениях добавляют следующую миграцию, а не переписывают уже применённую историю без необходимости.

### 74. Зачем journal JSON?

Хостинг использует имя и порядок миграции. Tag соответствует SQL-файлу, idx задаёт номер, when является служебной меткой. Это не список советов и не автоматически обновляемая база пользователей.

### 75. Используем Drizzle ORM?

В runtime-коде нет его импортов и зависимостей. SQL выполняется напрямую через подготовленные выражения. Папка drizzle и её журнал используются как формат доставки миграции для хостинга.

### 76. Почему локальная база синхронная, а обработчик async?

Node DatabaseSync выполняет операции синхронно и возвращает готовые результаты. Обёртка даёт общему обработчику похожий интерфейс. Await работает и с обычным значением, и с Promise, поэтому обработчик не нуждается в двух версиях бизнес-логики.

### 77. База создаётся при каждом запросе?

Нет. Локальная настройка сервера открывает её и применяет CREATE IF NOT EXISTS заранее. На хостинге таблица приходит миграцией. HandleSaved только читает и записывает строки.

### 78. Зачем close при остановке сервера?

Чтобы освободить SQLite-соединение. Локальная конфигурация подписывается на событие close HTTP-сервера, если он доступен. Это очистка серверного ресурса, не React-эффект страницы.

### 79. Почему нужен Node 24?

Так документирована и проверена локальная версия с встроенным node:sqlite. Требование сборщика Vite само по себе не описывает все требования нашего нового серверного кода. На хостинге Worker этот Node-модуль не включается в обработчик базы.

### 80. Что входит в Worker?

Содержимое обработчиков owl и saved, таблица собранных статических ресурсов и маршрутизация запросов. Local-db.js туда не вставляется: он нужен только Node-серверу разработки и preview.

### 81. Как проверяется вход POST?

Проверяются метод, Origin при наличии, DB, длина текстового тела, ожидаемые source и строковый text после trim. SQL дополнительно ограничивает источник и длину. Нельзя полагаться только на то, что фронтенд отправит правильные props.

### 82. Ограничение body.length измеряет байты?

Нет. Это длина JavaScript-строки в кодовых единицах UTF-16. Нельзя называть это полноценным сетевым лимитом памяти. На сервере тело читается до этой проверки; локальный адаптер также ограничивает накопленную строку.

### 83. Проверка Origin является авторизацией?

Нет. Она отклоняет присутствующий несовпадающий Origin, но запрос без него разрешён, а вне браузера заголовки можно задать. Доступ владельца к опубликованному сайту регулирует хостинг отдельно.

### 84. Можно подделать источник совета в API?

Маршрут принимает source из допустимого списка и текст клиента, но не проверяет криптографически происхождение внешнего ответа. Это учебная общая копилка, а не заверенный архив высказываний.

### 85. Где хранится ключ совы?

В серверном окружении. Клиент отправляет только question своему маршруту. Переменная с префиксом VITE_ могла бы попасть в браузерную сборку, поэтому для секрета этот префикс не используется.

### 86. Все HTTP-запросы вообще идут через Axios?

Все браузерные API-функции используют общий Axios instance внутри query/mutation. Сервер обращается к внешней модели через fetch и к D1 через её binding. Эти внутренние операции backend не являются самостоятельными запросами React в обход TanStack Query.

### 87. Зачем сохранён request interceptor?

Он по-прежнему показывает метод и адрес Axios-запроса. Query-библиотека не заменяет этот транспортный механизм. По Console можно проследить реальные клиентские вызовы.

### 88. Что происходит при ошибке JSON?

API-функции проверяют ожидаемые поля и выбрасывают исключение. Axios-ошибка проходит через общий interceptor, а ошибки собственной проверки после ответа ловит query-библиотека. Отсутствие ожидаемого поля не превращается молча в успешный текст.

### 89. Чем пустота отличается от ошибки?

Успешный массив [] означает отсутствие записей и даёт отдельное сообщение. Ошибка соединения, HTTP-статуса или формата идёт по ошибочной ветке. Для пустоты не нужно показывать «Источник недоступен».

### 90. Почему иногда видны два начала запроса в разработке?

Корневой StrictMode проверяет жизненный цикл компонентов дополнительными действиями в development. TanStack Query также работает с подписками и сигналом отмены. Нужно смотреть отмену и фактические завершения, а не объявлять любой повтор бесконечным циклом. Это не обещание двойного запроса в production.

### 91. Что происходит с отменённой ошибкой Axios?

Interceptor не переписывает сообщение ERR_CANCELED как обычную недоступность. Query-библиотека управляет отменой своего query. В нашем хуке больше нет самостоятельного catch, который должен вручную обслуживать её состояние.

### 92. Что произойдёт при обновлении браузера после сохранения?

Фильтр и обычный кеш памяти создадутся заново. GET прочитает сохранённую серверную запись. Если база доступна, запись останется. Эти два разных вида сохранения нельзя смешивать.

### 93. Почему не добавили удаление?

Условие требует одно действие создания, изменения или удаления через mutation. Мы выбрали создание. Дополнительные кнопки и маршруты увеличили бы код без необходимости для выбранной демонстрации.

### 94. Почему не localStorage для всей копилки?

Тогда изменялись бы только данные браузера. Задание на 5 требует действие на сервере по HTTP и обновление связанных данных через инвалидацию. Реальная серверная база соответствует этому сценарию.

### 95. Что доказывает успешный npm run build?

Исходники удалось обработать, клиент и Worker собраны. Это не доказывает доступность внешнего API, корректную квоту ключа или успешную авторизацию посетителя. Эти уровни проверяются отдельно.

### 96. Почему localhost и опубликованный сайт показывают разные записи?

У них отдельные базы. Это ожидаемо и удобно для разработки. Чтобы увидеть запись на опубликованном сайте, сохранить её нужно через его API, а не только через локальный маршрут.

### 97. Если сова вернула 502, значит Router сломан?

Нет. Сначала смотри, какой запрос завершился ошибкой. POST /api/owl с 502 относится к серверному обращению к внешнему источнику. Маршрутизация страниц и копилка могут продолжать работать. Однако живую успешную генерацию перед защитой нужно проверить отдельно.

### 98. Если сайт без входа вернул 403, значит API сломан?

Не обязательно. У опубликованного сайта сохранён доступ владельца. Хостинг может отклонить запрос до приложения. Это отличается от 403 самого handleSaved при несовпадающем Origin. Не меняй аудиторию сайта ради проверки без отдельного решения пользователя.

### 99. Почему нет node_modules, dist и SQLite-файла в Git?

Это установленные зависимости, результат сборки и локальные runtime-данные. Они не являются собственным исходным кодом. Package.json, SQL и серверные модули позволяют подготовить среду и заново запустить проект.

### 100. Как доказать, что реализован именно пункт на 5?

Показать query-хуки вместо сетевого эффекта, один кеш QueryClient, реальные HTTP-чтения, mutation с ожиданием и ошибкой, серверную запись и последующую инвалидацию. Затем открыть Zustand и убедиться, что ответов API в нём нет. Одной установленной библиотеки недостаточно.

## 20. Что не надо говорить на защите

| Неточная формулировка | Как объяснить правильно |
| --- | --- |
| Все данные теперь в Zustand | Там только общий фильтр, серверные данные в query-кеше |
| QueryClient создаётся для каждой страницы | Один клиент создан на уровне модуля и передан провайдеру |
| POST автоматически означает useMutation | Важно назначение операции; сохранение записи у нас mutation |
| staleTime удаляет данные через минуту | Он определяет свежесть, удаление неактивного кеша связано с gcTime |
| Через минуту запрос обязательно пойдёт сам | Истечение свежести не равно интервальному опросу |
| Инвалидация всегда немедленно отправляет GET | Для неактивной копилки запрос обычно будет при открытии |
| Кеш TanStack Query и HTTP-кеш одно и то же | Это разные механизмы с разными настройками |
| Фильтр сохраняется навсегда | Сохраняется между переходами, но не после полного reload |
| Форма сохраняется так же, как фильтр | Её локальное состояние сбрасывается при размонтировании |
| При выборе совы запрос Канье не выполняется | Фильтр скрывает карточку, запросы организованы независимо |
| SHA-256 шифрует совет | Он создаёт стабильный id, текст отдельно хранится открыто |
| У каждого посетителя своя копилка | В текущей таблице нет userId, копилка общая |
| После сохранения на localhost запись видна на хостинге | Это разные базы |
| В проекте ORM, потому что есть drizzle | Здесь прямой SQL, папка содержит миграцию и журнал |
| Все внешние сервисы были проверены успешно | При последней реализации живые внешние ответы проверить не удалось, успешные операции копилки проверены отдельно |

## 21. Честные ограничения и результаты проверки снимка

На момент подготовки шестой лабораторной были выполнены автоматические сценарии компонентов с управляемыми HTTP-ответами. Проверялись первоначальная загрузка, валидация формы, независимые карточки, общий фильтр, ошибки и повтор, старый отправленный вопрос, пустота, mutation, кеш, инвалидация, переходы и история браузера. Это проверка логики в DOM-окружении, а не полноценная визуальная проверка в настоящем браузере.

Сервер проверялся с настоящей SQLite-таблицей: чтение, запись, валидация, одинаковый id и отсутствие дубликата. На опубликованном сайте подтверждены таблица D1, прямые HTML-адреса, GET копилки, успешный POST, чтение сохранённой строки и отсутствие повторной строки.

В опубликованной копилке была оставлена явно подписанная запись «Проверка копилки: сохранение на сервере работает. Вжих-вжих!». Она является проверочной записью, а не доказательством успешной генерации внешней моделью.

При той живой проверке сова вернула 502, а запрос Канье из проверочного окружения получил 403. Поэтому нельзя утверждать, что успешные ответы обоих внешних API в опубликованной версии тогда были подтверждены. Эти ошибки не подменяются локальными выдуманными ответами. Перед защитой проверь доступность источников заново в своём браузере. Этот документ не выполняет новые живые запросы и не сообщает новый статус сервисов.

Другие границы:

- У копилки нет аккаунтов, редактирования, удаления и пагинации.
- Весь список фильтруется на клиенте; для маленького проекта этого достаточно.
- Store не валидирует произвольный вызов setSource из чужого кода, UI предлагает только три допустимые строки.
- SaveAdvice доверяет успешному телу своего сервера без отдельной строгой схемы. Чтение getSaved проверяет базовую форму массива, но не доказывает уникальность всех id и происхождение текста.
- Успех кнопки локален экземпляру компонента. Серверная защита от дубликата действует независимо.
- Новая запись не является уведомлением всем одновременно открытым браузерам. Механизма WebSocket и мгновенной межпользовательской синхронизации нет.
- Обновление списка зависит от query-настроек и действий. Это не круглосуточный опрос сервера.
- Origin-проверка не заменяет полноценную авторизацию. Приватный доступ хостинга настраивается отдельно.
- SQL-операции синхронны в локальном Node-адаптере. Для маленькой учебной базы это проще, но не претендует на высокую нагрузку.
- Промт совы задаёт желаемый стиль, но не формально гарантирует количество предложений. Замена Unicode-тире дополнительно выполняется кодом сервера.
- Build-скрипт обслуживает небольшой сайт и упаковывает статику в Worker; для больших файлов обычно выбирают другую организацию ресурсов.

## 23. Как запустить и не запутаться в версиях

Проверь Node и npm:

```bash
node --version
npm --version
```

Для этой версии используй Node.js 24. В папке проекта:

```bash
npm install
npm run dev
```

Открой адрес, напечатанный Vite. Порт может отличаться от прежнего, если он занят. Оставь терминал сервера работающим. Остановить его можно Ctrl+C. Файл `.env.local` задаёт локальные серверные переменные, в Git его не добавляем. После изменения окружения сервер обычно нужно перезапустить.

Для проверки сборки:

```bash
npm run build
npm run preview
```

Build собирает клиент и Worker, preview показывает локальную сборку с API-адаптером. Ни одна из этих команд не отправляет изменения в GitHub и сама по себе не публикует сайт на Sites.

Нормально, что npm создаёт node_modules и lock-файл. Это файлы инструментов, а не вручную написанная программа. В этом репозитории они игнорируются по принятому решению. В обычных проектах lock-файл часто сохраняют для точного воспроизведения зависимостей.

Ветка lab6-state отделяет новые изменения от завершённого снимка пятой лабы. Для подготовки к защите открывай именно текущие файлы этой ветки, а не старый master с другим устройством useAdvice.

## 25. Короткая памятка

- Общий фильтр: Zustand, одна строка source.
- Страницы: BrowserRouter, Routes, NavLink, wildcard.
- Серверные данные: TanStack Query, без дублирования в store.
- Чтение: useQuery; сохранение: useMutation.
- HTTP: API-функции и общий Axios.
- Кеш: fresh 60 секунд, неактивный gc по умолчанию около 5 минут.
- Повтор: refetch; автоматический retry отключён.
- После записи: invalidateQueries по `['saved']`.
- Настоящее хранение: D1 на хостинге, SQLite локально.
- Одинаковый нормализованный текст: одинаковый id и одна строка.
- Проверка прямой ссылки: HTML fallback сервера плюс Router.
- Не обещаем успешную работу внешнего API без живой проверки.
