# Лабораторная 7: как спокойно пройти защиту

Это маршрут защиты: куда нажимать, какой файл открывать и что объяснять преподавателю. Здесь не нужно пересказывать весь проект. Главная задача - показать, что ты понимаешь, зачем добавил типы и какие ошибки они помогают заметить.

Сначала прочитай этот файл. Если какое-то объяснение осталось непонятным, открой `02-defense-guide.md`. Если нужно разобрать конкретную строку, открой `01-line-by-line.md`.

## 1. Главная мысль, которую надо держать в голове

В прошлой работе приложение уже работало. В этой работе мы описали, какие данные должны быть в разных местах программы.

Пример: у совета есть текст и идентификатор. У сохранённого совета есть ещё источник. Источником может быть сова или Канье. Если случайно написать другой источник или передать число вместо текста, TypeScript поможет заметить это до запуска страницы.

Но TypeScript не управляет внешним сервером. Сервер всё равно может прислать неправильный ответ. Поэтому ответы API мы отдельно проверяем обычными условиями.

Если понимаешь эти два предложения, уже понимаешь основу лабораторной:

> TypeScript проверяет, правильно ли я написал программу. А проверки ответа API проверяют данные, которые пришли во время её работы.

## 2. Что подготовить до начала защиты

Открой проект в редакторе и заранее найди эти файлы:

1. `package.json` и `tsconfig.json`.
2. `src/types/advice.ts`.
3. `src/api/advice.ts` и `src/api/validation.ts`.
4. `src/utils/toArray.ts`.
5. `src/hooks/useAdvice.ts` и `src/components/AdviceResult.tsx`.
6. `src/pages/SavedPage.tsx`.
7. `src/shared/Button.tsx`.

В браузере открой главную страницу и копилку. В терминале перейди в папку проекта.

До защиты проверь:

```bash
npm ci
npm run typecheck
npm test
npm run build
```

Чистую установку через `npm ci` удобнее сделать заранее, чтобы не ждать загрузки пакетов перед преподавателем. На самой защите достаточно быстро показать `npm run typecheck`, а вывод предыдущих проверок держать под рукой.

Если показываешь локальную версию, запусти:

```bash
npm run dev
```

Локальный сайт и опубликованный сайт имеют разные настройки ключа и разные базы копилки. Запись, сохранённая на компьютере, не обязана появиться на опубликованном сайте. Это не ошибка TypeScript.

## 3. В каком порядке двигаться

Не открывай сразу все файлы подряд. Двигайся по одной истории: есть совет, он приходит с сервера, проверяется и показывается пользователю.

| Остановка | Что показываешь | Что преподаватель должен понять |
| --- | --- | --- |
| 1 | Сайт | Это продолжение предыдущего проекта |
| 2 | Команду typecheck и настройки | Проверка типов действительно подключена |
| 3 | Общие типы | Ты описал свои данные, а не только переименовал файлы |
| 4 | Запрос и проверки ответа | Ты различаешь типы и реальные внешние данные |
| 5 | Generic | Собственная функция действительно используется |
| 6 | Состояния карточки | Ты понимаешь union и проверку status |
| 7 | Числовое поле | Ты умеешь обрабатывать строку, событие и число |
| 8 | Общую кнопку | Ты используешь типы React без ручного дублирования |
| 9 | Намеренную ошибку | Компилятор действительно замечает неправильное значение |

Полный маршрут займёт примерно 7-10 минут, если не читать каждую строку вслух. Если преподаватель задаёт вопросы, остановись на его вопросе, а потом продолжи со следующей остановки.

## 4. Остановка 1: начать с работающей страницы

**Что сделать.** Покажи главную и перейди в копилку. Достаточно коротко показать вопрос, ответы и сохранённые записи.

**Что сказать.**

> Это мой проект из предыдущей лабораторной. Сова отвечает на вопрос, второй источник даёт случайную цитату, понравившийся текст можно сохранить в копилку. В седьмой работе я сохранил эту логику и перевёл клиентскую часть на TypeScript.

**Как это работает простыми словами.** Страница собирается из компонентов. Один компонент отвечает за форму, другой за карточку, другой за сохранение. Типы описывают, какие данные они передают друг другу.

Не трать несколько минут на оформление совы, анимацию и дисклеймер. Они помогают узнать проект, но тема этой работы - типизация.

**Переход к следующему шагу.**

> Сначала покажу, как запускается проверка типов, потом разберу один ответ от запроса до карточки.

Это фрагмент настроек. Для проверки используется полный `tsconfig.json` проекта.

**Что сказать про них.**

**Если спросят, где это пригодилось.** Укажи на проверку `root === null` в `src/main.tsx` и запасную позу `moments[step] ?? idle` в `src/components/Owl.tsx`.

Скажи точно: конфигурация проверяет клиентскую папку `src`. Серверные адаптеры и скрипт упаковки остались на JavaScript от прошлой работы.

## 6. Остановка 3: объяснить, что такое совет в программе

**Что открыть.** `src/types/advice.ts`.

Покажи этот блок:

```ts
export type AdviceSource = 'owl' | 'kanye'

export interface Advice {
  id: string
  text: string
}

export interface SavedAdvice extends Advice {
  source: AdviceSource
}
```

**Что сказать.**

> Здесь описана главная сущность моего приложения - совет. У обычного ответа есть строковый id и текст. У сохранённого совета дополнительно есть источник. extends позволяет взять поля обычного совета и добавить новое поле, не переписывая старые.

Покажи первую строку:

> Источник может иметь только два значения: owl или kanye. Вертикальная черта означает «или». Если я напишу другой источник, проверка типов покажет ошибку.

### Тут же закрыть вопросы про Pick, Omit и Record

Ниже в том же файле покажи:

```ts
export type NewAdvice = Pick<SavedAdvice, 'source' | 'text'>

export type AdviceTextProps = Omit<SavedAdvice, 'id'>

export const sourceNames: Record<AdviceSource, string> = {
  owl: 'Сова',
  kanye: 'Канье',
}
```

**Что сказать.**

> Pick выбирает нужные поля. Для добавления совета я отправляю источник и текст, а id получаю от сервера. Omit убирает ненужное поле: компоненту текста не нужен id. Record описывает словарь названий, в котором для каждого источника есть строка.

Не нужно объяснять эти утилиты на отвлечённых примерах с животными и машинами. У тебя уже есть настоящие примеры из своего проекта.

**Если спросят про type и interface.**

> Interface я использовал для объектов с полями. Type - для вариантов значений и сочетаний типов. В моём проекте так проще различать их назначение.

## 7. Остановка 4: пройти путь одного ответа

**Что открыть.** `src/api/advice.ts`. Покажи функцию `getOwl` целиком.

**Сначала объясни историю без терминов.**

> Я отправляю вопрос своему серверу. Ответ сначала считаю неизвестным. Проверяю, что пришёл объект с текстом совета. После проверки делаю из него объект понятной приложению формы и отдаю список карточке.

Теперь покажи конкретные места в коде:

```ts
export async function getOwl(signal?: AbortSignal, question = ''): Promise<Advice[]> {
  const { data } = await http.post<unknown>('/api/owl', { question }, { signal })
  if (data === null || (Array.isArray(data) && data.length === 0)) return []
  if (!isRecord(data) || typeof data.advice !== 'string') {
    throw new Error('Сова прислала непонятный ответ.')
  }
  if (!data.advice.trim()) return []
  return toArray<Advice>({ id: 'owl', text: data.advice })
}
```

**Что сказать про Promise.**

> Ответ приходит не сразу. Поэтому функция возвращает Promise. После успешного ожидания результатом будет массив Advice. Если сеть или проверка ответа дадут ошибку, успешного массива не будет, и Query покажет ошибку.

**Что сказать про unknown.**

> Тип unknown означает, что данные пришли, но я ещё не знаю, можно ли доверять их форме. Я не могу сразу обращаться с ними как с готовым советом. Сначала выполняю проверки.

**Что сказать про пустоту.**

> Пустой ответ и ошибка - разные случаи. Пустой результат становится пустым массивом. Неправильная форма ответа становится Error.

### Открыть проверку объекта

Перейди в `src/api/validation.ts`:

```ts
export function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null && !Array.isArray(value)
}
```

**Что сказать.**

> Проверяю, что это объект, но не null и не массив. Null проверяю отдельно, потому что JavaScript тоже называет его объектом через typeof. После проверки можно посмотреть свойства объекта, а затем проверить сами свойства.

**Самый вероятный вопрос преподавателя.** «Зачем проверять, если ты уже написал тип Advice?»

**Ответ.**

> Тип проверяет мой код во время разработки. Он не меняет ответ чужого сервера. Поэтому внешние данные надо проверить ещё и во время работы программы.

На этом шаге не уходи в устройство нейросети или хранение ключей. Для этой лабораторной достаточно объяснить границу между неизвестным ответом и проверенными данными.

## 8. Остановка 5: свой generic, который легко объяснить

**Что открыть.** `src/utils/toArray.ts`.

```ts
export function toArray<T>(value: T | T[]): T[] {
  return Array.isArray(value) ? value : [value]
}
```

**Что сказать.**

> Карточка работает со списком, а сервис возвращает один совет. Эта функция превращает одно значение в массив. Если ей уже передали массив, она оставляет его массивом. Буква T означает тип элемента, который подставляется при вызове.

Вернись на последнюю строку `getOwl` и покажи применение:

```ts
return toArray<Advice>({ id: 'owl', text: data.advice })
```

**Что добавить.**

> В этом вызове вместо T используется Advice. Поэтому на выходе массив советов, а не список неизвестных значений. Функция реально используется и для совы, и для цитаты.

**Если забудешь слово generic.** Скажи сначала: «Это функция, которой я задаю тип элемента». Затем добавь название. Объяснение действия важнее быстрого произношения термина.

## 9. Остановка 6: как приложение понимает, что показывать

**Что открыть.** Сначала `src/types/advice.ts`, блок `AdviceState`.

```ts
export type AdviceState =
  | { status: 'loading' }
  | { status: 'error'; error: string }
  | { status: 'empty' }
  | { status: 'success'; data: Advice[] }
```

**Что сказать.**

> У результата четыре варианта. Пока ждём, есть loading. Если произошла ошибка, есть error и сообщение. Если ответ пустой, есть empty. Если ответ получен, есть success и массив данных.

Дальше главное объяснение:

> Я связал поля со статусом. Данные есть только у success, сообщение ошибки только у error. Благодаря этому нельзя случайно прочитать результат до его получения.

**Теперь открыть.** `src/components/AdviceResult.tsx`, весь `switch (result.status)`.

**Что сказать, показывая ветки.**

> Здесь по статусу выбирается содержимое карточки. В loading показывается ожидание, в error сообщение и повтор, в empty сообщение о пустоте. Только в success я обращаюсь к result.data и вывожу список через map.

**Как объяснить сложное название.**

> Это union с полем-меткой. Метка status помогает отличить варианты объекта. После её проверки TypeScript понимает, какие поля доступны. Такой тип называют discriminated union.

**Если спросят про амперсанд.** Покажи конец типа `AdviceResultData`:

```ts
export type AdviceResultData = {
  id: AdviceSource
  title: string
  method: string
} & AdviceState
```

> У карточки всегда есть источник, заголовок и подпись. Амперсанд соединяет эти общие поля с одним из вариантов состояния.

**Если спросят, где хранятся данные.** Открой `src/hooks/useAdvice.ts`:

> Серверные данные хранит TanStack Query. У запросов указаны Advice[] и Error. В Zustand храню только общий фильтр, а в useState черновик формы и число. Я не делаю несколько копий одного списка в разных хранилищах.

## 10. Остановка 7: показать числовое поле руками

**Что сделать в браузере.** Открой копилку. В поле количества записей по очереди введи:

1. `2` - должны остаться максимум две записи.
2. `0` - должно появиться сообщение о неправильном числе.
3. `2.5` - дробное число тоже не подходит.
4. Очисти поле - пустота тоже должна дать сообщение.
5. Введи `10` - ошибка должна исчезнуть.

Если в копилке только одна запись, значение 2 не создаст вторую. Оно задаёт верхнюю границу показа, а не число новых записей.

**Что сказать.**

> Я добавил выбор количества показанных советов. Ввод принимаю строкой, потом превращаю в число и проверяю. Разрешено только целое число от 1 до 50. Неправильный ввод не удаляет записи из базы, а показывает ошибку.

**Что открыть в коде.** `src/pages/SavedPage.tsx`.

Сначала покажи состояния:

```tsx
const [limitInput, setLimitInput] = useState('10')
const [limit, setLimit] = useState<number | null>(10)
```

**Что сказать.**

> Первая переменная хранит то, что ввёл пользователь, как строку. Вторая хранит проверенное число. Если ввод неверный, вместо числа ставлю null. Здесь тип useState указан явно, потому что начальное 10 не показывает возможность null.

Потом покажи обработчик целиком:

```tsx
function handleLimitChange(event: ChangeEvent<HTMLInputElement>): void {
  const text = event.target.value
  setLimitInput(text)
  const number = Number(text)
  if (!text.trim() || !Number.isInteger(number) || number < 1 || number > 50) {
    setLimit(null)
    return
  }
  setLimit(number)
}
```

**Разбор устно без сложных слов.**

> Событие относится к обычному input. Беру его value, сохраняю строку, преобразую через Number. Потом проверяю, что строка не пустая, число целое и входит в диапазон. Если проверка не прошла, ставлю null и выхожу. Если всё правильно, сохраняю число.

**Вероятный вопрос.** «Почему строка, если type у поля number?»

> Потому что свойство value у поля ввода всё равно строка. Number выполняет настоящее преобразование. Тип TypeScript сам строку в число не превращает.

**Ещё один вопрос.** «Разве min и max не проверяют это сами?»

> Они помогают браузеру, но в обработчике я всё равно проверяю полученное значение. Поведение моей программы не должно зависеть только от подсказок HTML.

## 11. Остановка 8: типы React на общей кнопке

**Что открыть.** `src/shared/Button.tsx`.

```tsx
import type { ComponentProps, ReactNode } from 'react'

type ButtonProps = ComponentProps<'button'> & { children: ReactNode }

export function Button({ children, type = 'button', ...props }: ButtonProps) {
  return <button type={type} className="retro-button" {...props}>{children}</button>
}
```

**Что сказать.**

> Для обычной кнопки уже существуют готовые типы React. ComponentProps берёт стандартные свойства button: например disabled и onClick. Я не описываю их вручную второй раз. ReactNode описывает содержимое, которое React умеет показать внутри кнопки.

**Если спросят про children.**

> Это то, что передают между открывающим и закрывающим тегом Button. У меня обычно текст кнопки, но тип допускает и другие подходящие React-элементы.

**Если спросят про props и callbacks.** Открой начало `src/components/AdviceForm.tsx`:

> Props описывают вход компонента. Форма получает строку вопроса и функции. Одна функция принимает новую строку, другая событие отправки формы. Такие подписи помогают не перепутать, какой аргумент кому передавать.

## 12. Остановка 9: намеренная ошибка компилятора

По заданию нужно показать не только успешную команду, но и осмысленную ошибку. Выбери маленький пример, который легко вернуть в правильное состояние.

**Что сделать.** Временно создай файл `src/lab7-error-demo.ts`:

```ts
import type { AdviceSource } from './types/advice'

const source: AdviceSource = 'cat'
console.log(source)
```

Выполни:

```bash
npm run typecheck
```

Компилятор должен сообщить TS2322: строка cat не подходит типу AdviceSource. Номер строки в сообщении зависит от пустых строк в созданном файле.

**Что сказать.**

> Слева я обещал допустимый источник, а справа написал значение, которого в списке нет. Компилятор показывает место несовместимого присваивания. Это обычная опечатка, которую теперь можно найти до запуска страницы.

**Как закончить демонстрацию.** Замени `'cat'` на `'owl'` и запусти команду снова. Она должна пройти. Затем удали временный учебный файл и ещё раз проверь typecheck.

Не оставляй намеренную ошибку в сдаваемой версии. Не пытайся исправить её отключением проверки. В этом примере правильное исправление - выбрать разрешённое значение.

## 13. Как закончить защиту

Не надо заново перечислять каждую строку. Свяжи показанные части в одно объяснение:

> Я описал данные советов и договоры между компонентами. Внешний ответ сначала проверяю, затем передаю в типизированные запросы и карточки. Состояния разделены по status, поэтому нужные поля читаются только в подходящей ветке. Число из формы преобразую и проверяю отдельно. Проверка типов проходит после чистой установки, а намеренная ошибка показывает, что она действительно работает.

Покажи успешный `npm run typecheck` после исправления примера. Ссылку на репозиторий, лог команды и короткую записку подготовь к сдаче. Записка уже есть в конце `02-defense-guide.md`, её можно адаптировать под свои слова.

## 14. Если преподаватель начинает спрашивать не по твоему порядку

Не пытайся любой ценой дочитать заготовленную речь. Ответь на вопрос через один конкретный пример своего проекта.

## 15. Если API не ответил на защите

Спокойно покажи сообщение ошибки. Не говори, что генерация прошла, если её нет.

> Внешний сервис сейчас не ответил. Это обработано отдельным состоянием ошибки. Типизация при этом проверяется независимо: я могу показать typecheck, проверки данных и числовое поле копилки.

Если копилка тоже временно недоступна, проверку числового поля всё равно можно показать: неправильное число имеет своё сообщение. Но наличие сохранённых записей и успешное чтение в такой момент не обещай.

Собственный код и стабильность внешнего провайдера являются разными вопросами. На этой защите ты объясняешь, как программа устроена и как она реагирует на оба результата запроса: успех и ошибку.

## 16. Если забыл термин или растерялся

Сначала объясни действие обычными словами. Потом, если вспомнил, назови термин.

- Вместо «я применил discriminated union» начни с «у ответа несколько вариантов, я отличаю их по status».
- Вместо «происходит narrowing» начни с «после этой проверки компилятор знает, что значение подходит».
- Вместо «использовал generic» начни с «эта функция подходит разным типам элементов и сохраняет их тип».
- Вместо «nullable state» начни с «здесь может быть число или null, если ввод неправильный».

Не нужно подбирать длинные определения. Объяснение должно совпадать с кодом, который открыт перед преподавателем.

Если не уверен в детали, покажи конкретную строку и пройди её по порядку: что приходит, что проверяется, что возвращается. Это надёжнее, чем угадывать ответ про библиотеку целиком.

## 17. Что не стоит говорить

| Неточная фраза | Как сказать правильно |
| --- | --- |
| TypeScript проверил ответ сервера | Я проверил ответ обычными условиями, а TypeScript помог дальше правильно использовать результат |
| Тип сам превратил строку в число | Строку преобразовала функция Number, потом я проверил число |
| Все данные лежат в Zustand | В Zustand общий фильтр, в Query серверные ответы, в useState локальный ввод |
| У меня весь сервер на TypeScript | В этой работе я перевёл React-клиент; серверные адаптеры остались от предыдущей работы |
| Generic проверяет JSON | Generic сохраняет тип, а JSON проверяется отдельными условиями |
| Promise гарантирует успешный ответ | Promise описывает будущий результат, но может завершиться ошибкой |
| Я переписал весь проект заново | Я продолжил предыдущий проект и добавил типизацию |
