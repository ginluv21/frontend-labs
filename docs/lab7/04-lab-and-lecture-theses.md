В лекции примеры про книги, карточки и корзину. У нас вместо книги совет, вместо каталога ответы, вместо добавления книги сохранение совета. Объяснение ниже построено на нашем коде. Примеры из лекции не выдаются за функции, которых в проекте нет.

## 1. Сначала вся работа в одной истории

**Как объяснить:**

> Смотри, раньше у меня уже был сайт с совой. Он отправлял вопрос, получал ответ и мог сохранить его в копилку. В этой работе я не стал делать другой сайт. Я описал, какие значения должны передаваться между частями старого.
>
> Например, текст совета должен быть строкой. Источник должен быть либо совой, либо Канье. Если я случайно передам число вместо текста или ошибусь в названии источника, TypeScript сможет заметить это до запуска страницы.
>
> Но сервер тоже может прислать что-нибудь неправильное. Поэтому ответ сервера я отдельно проверяю обычными условиями. Когда данные прошли проверку, передаю их в карточку и показываю.

Это основная история всей лабораторной. Дальше каждый пункт задания раскрывает какую-то её часть.

## 4. Пункт задания: .tsx, tsconfig.json и typecheck

**Где показать:** файлы в `src`, `tsconfig.json`, `package.json`.

**Как объяснить:**

> В файлах `.tsx` у меня компоненты с JSX. В `.ts` обычные функции и типы. В tsconfig находятся настройки проверки. А команда typecheck запускает проверку для всего клиента, чтобы не искать ошибки только по подчёркиваниям в редакторе.

В `package.json` есть команда:

```json
"typecheck": "tsc --noEmit"
```

Это строка внутри объекта scripts. Для запуска набираем:

```bash
npm run typecheck
```

`tsc` - компилятор TypeScript. `--noEmit` просит его проверять код без записи выходных файлов.

**Логика по шагам:**

1. Команда находит настройки проекта.
2. Проверяет файлы, включённые в `tsconfig.json`.
3. Если видит несовместимые типы, пишет место и причину ошибки.
4. Если ошибок нет, завершается успешно.

**Связь с лекцией:** у проверки типов и получения JavaScript разные задачи. В лекции есть отдельный пример запуска `tsc` и отдельное объяснение работы со сборщиком в React. У нас используется вариант для React: TypeScript проверяет, Vite собирает.

### Важная деталь лекции: noEmit и noEmitOnError не одно и то же

**Как объяснить:**

> noEmit вообще не создаёт выходные JavaScript-файлы. noEmitOnError запрещает создавать их при ошибках, когда компилятор используется ещё и для выпуска JavaScript. У меня выпуском занимается Vite, поэтому TypeScript запускается только для проверки.

Наша сборка начинается так:

```json
"build": "npm run typecheck && vite build && node scripts/build-server.mjs"
```

`&&` означает: переходить к следующей команде только после успеха предыдущей. Поэтому ошибка typecheck остановит сборку.

## 5. Пункт задания: типы основной сущности в данных и props

**Где показать:** `src/types/advice.ts`, `src/hooks/useAdvice.ts`, `src/components/AdviceResult.tsx`.

```ts
export interface Advice {
  id: string
  text: string
}

export interface SavedAdvice extends Advice {
  source: AdviceSource
}
```

**Как объяснить:**

> Совет у меня обычный объект. В описании я указал, что у него есть строковые id и text. У сохранённого совета есть ещё источник. Теперь эти сведения не нужно заново придумывать в каждом компоненте.

**Что происходит дальше:** API-функция возвращает массив `Advice[]`. Типизированный запрос хранит такой массив в состоянии Query. Карточка получает результат с этими данными через props.

**Почему не сделан отдельный useState со вторым списком:**

> Ответы сервера у меня уже хранятся в Query с прошлой лабы. Я типизировал это состояние, а не стал делать ещё одну копию того же списка в useState.

Здесь `Advice[]` читается как «массив советов». Это не другой вид объекта Advice, а список таких объектов.

Связь с лекцией: один тип книги используется в нескольких местах приложения. У нас точно так же переиспользуется тип совета.

## 6. Пункт задания: props и callbacks

**Где показать:** `src/components/AdviceForm.tsx`.

```ts
interface AdviceFormProps {
  question: string
  onQuestionChange: (question: string) => void
  onSubmit: (event: FormEvent<HTMLFormElement>) => void
  error: string
  loading: boolean
}
```

**Как объяснить:**

> Props - это то, что родитель передаёт компоненту. Моей форме нужны вопрос, сообщение ошибки и признак загрузки. Ещё ей передаются две функции. Когда текст меняется, форма вызывает первую функцию и отдаёт новую строку. Когда отправляется форма, вызывает вторую и передаёт событие отправки.

Прочитай подпись:

```ts
onQuestionChange: (question: string) => void
```

Обычными словами: «Это функция, которой можно передать строку. Вызывающий код не рассчитывает получить от неё полезный результат».

**Как оно работает:** форма не получает полный доступ к состоянию родителя. Она получает конкретную функцию. Родитель решает, как сохранить переданный текст.

**Что такое callback:** функция, которую передали, чтобы другая часть программы вызвала её в подходящий момент.

**Что означает void:** здесь описано, что результат вызова не используется как полезное значение. Это не запрет на любые побочные действия: функция как раз может обновить состояние.

Связь с лекцией: там callback добавления получает id книги. Здесь callback изменения вопроса получает текст, а действие фильтра получает разрешённый источник. Смысл один: заранее известно, что можно передать функции.

## 7. Пункт задания: useState там, где вывода типа недостаточно

**Где показать:** `src/pages/SavedPage.tsx`.

```tsx
const [limitInput, setLimitInput] = useState('10')
const [limit, setLimit] = useState<number | null>(10)
```

**Как объяснить:**

> В первой строке всё понятно по начальному значению: это строка. TypeScript сам это видит. Во второй строке сначала тоже стоит 10, но позже я могу записать null, если пользователь ввёл неправильное число. Поэтому здесь я сразу написал: состояние допускает число или null.

**Почему нужен явный тип:** без `<number | null>` из начального 10 вывелся бы только `number`. Вызов `setLimit(null)` тогда не подошёл бы.

**Почему не стоит писать тип везде:**

> Если TypeScript и так правильно понял строку или число, я не дублирую очевидное. Явную подсказку даю там, где первое значение не показывает все возможные значения состояния.

Связь с лекцией: простые начальные значения позволяют вывести тип автоматически. Для пустого массива или состояния с null часто приходится явно описывать, что появится позже.

У нас нет нового локального массива книг из лекции. В нашем приложении список ответов уже принадлежит Query. Это применение той же идеи к другому месту хранения данных.

## 8. Пункт задания: число из формы, строка и ChangeEvent

**Где показать:** поле количества советов в копилке и обработчик в `src/pages/SavedPage.tsx`.

```tsx
function handleLimitChange(event: ChangeEvent<HTMLInputElement>): void {
  const text = event.target.value
  setLimitInput(text)
  const number = Number(text)
  if (!text.trim() || !Number.isInteger(number) || number < 1 || number > 50) {
    setLimit(null)
    return
  }
  setLimit(number)
}
```

**Как объяснить:**

> Смотри, даже у числового input значение value приходит строкой. Поэтому я сначала сохраняю исходный текст, а потом отдельно превращаю его в число. После этого проверяю, что поле не пустое, число целое и находится от 1 до 50.
>
> Если всё нормально, сохраняю число и показываю столько записей. Если нет, сохраняю null и показываю сообщение об ошибке.

**Зачем два состояния:** строка нужна, чтобы поле могло оставаться пустым во время редактирования. Проверенное число нужно для ограничения списка. Это разные представления одного ввода для разных задач.

**Что означает ChangeEvent<HTMLInputElement>:** событие изменения обычного HTML-поля input. Угловые скобки уточняют, к какому элементу относится событие.

**Откуда берутся типы:** `ChangeEvent` импортируется из React как тип. `HTMLInputElement` уже известен TypeScript из описаний браузерных элементов.

**Почему отдельно проверяется пустая строка:** `Number('')` даёт 0. Если не учитывать пустоту, легко начать путать очищенное поле с сознательно введённым числом.

**Почему проверяется Number.isInteger:** для количества записей подходит целое число. Две с половиной записи показать нельзя. Эта проверка также отклоняет NaN и бесконечность.

**Что показать руками:** ввести 2, затем 0, 2.5, очистить поле и вернуть 10. Правильный ввод ограничивает список, неправильный даёт сообщение.

Связь с лекцией: поле цены тоже даёт строку, а преобразование и проверка выполняются обычным JavaScript. Тип события не превращает текст в число.

## 9. Пункт задания: успешный typecheck, без any и @ts-ignore

**Где показать:** команду `npm run typecheck` и клиентские исходники.

**Как объяснить:**

> Я не просил компилятор игнорировать неудобные места. Если значение могло быть null или неизвестным объектом, я добавлял проверку. Если начального состояния не хватало, указывал подходящий тип.

**Что важно про any:** он позволяет использовать значение без подтверждения его формы. Это удобно, чтобы быстро убрать подчёркивание, но проблема от этого не исчезает.

**Что важно про unknown:** значение можно хранить и передавать, но перед чтением свойств его нужно проверить.

**Деталь из лекции, которую легко перепутать:** `strict` не запрещает любой явно написанный `any`. Например, явный any можно написать и в строгом проекте. Условие лабораторной «без any» мы соблюдаем отдельно, не используя его для обхода проверки.

`@ts-ignore` тоже не исправляет значение. Он скрывает диагностическое сообщение для строки. В этой работе такой способ не используется.

## 10. Пункт задания: Pick, Omit и Record

**Где показать:** `src/types/advice.ts`, `src/api/saved.ts`, `src/components/AdviceResult.tsx`.

```ts
export type NewAdvice = Pick<SavedAdvice, 'source' | 'text'>

export type AdviceTextProps = Omit<SavedAdvice, 'id'>

export const sourceNames: Record<AdviceSource, string> = {
  owl: 'Сова',
  kanye: 'Канье',
}
```

### Pick: выбрать нужные поля описания

**Как объяснить:**

> Для сохранения нового совета мне нужны источник и текст. Id выдаёт сервер. Поэтому я взял из SavedAdvice только source и text. Так функция сохранения сразу показывает, что от неё требуется на входе.

**Важная деталь лекции:** Pick создаёт новое описание типа. Он не делает копию объекта в памяти.

### Omit: убрать поле из описания

**Как объяснить:**

> Маленький компонент текста показывает текст и даёт сохранить его. Ему нужны text и source, а id не нужен. Поэтому его props описал как SavedAdvice без id.

**Важная деталь лекции:** Omit не удаляет поле из существующего объекта. Он только меняет описание того, что нужно принимающей части программы.

### Record: описать словарь

**Как объяснить:**

> Здесь для каждого источника есть название. Если ключ owl, получаю слово «Сова», если kanye - «Канье». Record проверяет, что я не забыл один из источников и что названия являются строками.

В нашей копилке используется:

```tsx
<h2>{sourceNames[item.source]}</h2>
```

Источник уже проверен, поэтому читаем название по известному ключу.

**Ещё одна деталь лекции:** словарь с любыми строковыми ключами может не содержать конкретный ключ. Тогда нужно запасное значение. Наш словарь описан по двум конкретным источникам, и для обоих значение обязательно.

## 11. Пункт задания: union состояния и разбор по значению

**Где показать:** `AdviceState` и `switch (result.status)`.

```ts
export type AdviceState =
  | { status: 'loading' }
  | { status: 'error'; error: string }
  | { status: 'empty' }
  | { status: 'success'; data: Advice[] }
```

**Как объяснить:**

> Я не сделал один объект, где могут одновременно лежать загрузка, ошибка и старый ответ. Я описал четыре варианта. Либо ждём, либо произошла ошибка, либо пришла пустота, либо есть успешный ответ.

Вертикальная черта означает «или». У каждого варианта своё содержимое.

**Как оно работает:** хук смотрит на состояние запроса и создаёт подходящий вариант. Карточка смотрит на status и выбирает, что показать.

В `src/hooks/useAdvice.ts`:

```ts
function getState(query: UseQueryResult<Advice[], Error>): AdviceState {
  if (query.isFetching || query.isPending) return { status: 'loading' }
  if (query.isError) return { status: 'error', error: getErrorMessage(query.error) }
  if (!query.data || query.data.length === 0) return { status: 'empty' }
  return { status: 'success', data: query.data }
}
```

**Объяснение этого блока:**

> Сначала проверяю, не ждём ли мы ответ. Потом проверяю ошибку. Потом пустые данные. Если эти случаи не подошли, значит можно отдать успешный результат с массивом.

В основной части лекции сначала вводятся допустимые строки статуса. В дополнительных примерах статус связывается с содержимым объекта. В проекте использован уже такой связанный вариант.

## 12. Пункт задания: type, interface, extends и &

**Где показать:** `src/types/advice.ts`.

**Как объяснить выбор:**

> Объекты с полями я описываю через interface. Набор допустимых строк и сочетания типов записываю через type. Оба подхода могут описывать объекты, просто в моём файле так понятнее, где что используется.

Не говори, что interface вообще нельзя использовать для props. Можно. И type тоже можно. Это отдельно подчёркивается в лекции.

### extends у сохранённого совета

```ts
export interface SavedAdvice extends Advice {
  source: AdviceSource
}
```

**Как объяснить:**

> У меня уже есть описание обычного совета. Я использую его поля и добавляю источник. Мне не надо заново писать id и text.

### & у карточки

```ts
export type AdviceResultData = {
  id: AdviceSource
  title: string
  method: string
} & AdviceState
```

**Как объяснить:**

> У каждой карточки всегда есть источник, заголовок и пояснение. К ним добавляется один вариант состояния. Амперсанд означает, что нужно и описание карточки, и подходящее состояние.

**Коротко для памяти:** `|` - выбираем вариант, `&` - совмещаем требования.

Типовое extends не создаёт экземпляры классов и не запускает наследование объектов в браузере. Здесь мы расширяем описание полей.

## 13. Пункт задания: strict и проверка null

**Где показать:** `tsconfig.json`, `src/main.tsx`, `src/api/validation.ts`.

```tsx
const root = document.getElementById('root')
if (root === null) throw new Error('Не найден элемент root.')
```

**Как объяснить:**

> Поиск элемента может ничего не найти. Тогда получится null. Я проверяю это до передачи элемента в React. Если элемент есть, идём дальше, если нет, получаем понятное сообщение.

**Как тип меняется после проверки:** до if root может быть элементом или null. Если дошли до следующей строки после проверки с throw, вариант null уже исключён.

В проверке внешнего объекта отдельно написано:

```ts
value !== null
```

Потому что `typeof null` в JavaScript даёт `'object'`. Одной проверки typeof недостаточно.

Связь с лекцией: отсутствие выбранной книги тоже считается отдельным состоянием. У нас та же идея встречается в отсутствии элемента root и в числе `number | null`.

## 14. Пункт задания: данные API как unknown, а не as

**Где показать:** `src/api/advice.ts`, `src/api/saved.ts`, `src/api/validation.ts`.

**Как объяснить:**

> Даже если я знаю адрес сервера, я ещё не знаю, что реально пришло в конкретном запросе. Поэтому получаю unknown. Дальше проверяю, что это объект, что нужные поля есть и имеют правильные типы. Только после этого возвращаю нормальные данные остальному приложению.

Полная проверка записи копилки:

```ts
export function readSavedAdvice(value: unknown): SavedAdvice {
  if (!isRecord(value) || typeof value.id !== 'string'
    || !isAdviceSource(value.source) || typeof value.text !== 'string') {
    throw new Error('Копилка прислала непонятный ответ.')
  }
  return { id: value.id, source: value.source, text: value.text }
}
```

**Как это объяснить по действиям:**

> Если это не объект, останавливаюсь. Если id не строка, тоже останавливаюсь. Источник должен быть одним из двух разрешённых. Текст должен быть строкой. После всех проверок собираю объект из проверенных полей.

**Что означает as в теме лекции:** это способ сказать компилятору, каким типом считать значение. Само значение от этого не изменится и не проверится.

**Как объяснить разницу:**

> Просто назвать данные советом недостаточно. Если внутри вместо текста число, оно от этого строкой не станет. Мне нужна настоящая проверка, а не просьба к компилятору поверить.

Дополнительные слайды лекции разбирают утверждения типа, пользовательские guards и проверку входящих данных. У нас isRecord и isAdviceSource используются именно для этой задачи.

### Что значит value is AdviceSource

```ts
export function isAdviceSource(value: unknown): value is AdviceSource {
  return value === 'owl' || value === 'kanye'
}
```

**Как объяснить:**

> Функция возвращает обычное true или false. Но её подпись дополнительно объясняет TypeScript: если проверка успешна, значение является допустимым источником. Поэтому после неё это значение можно передать в функцию фильтра.

Такая подпись сама не доказывает правильность тела функции. Проверку нужно написать честно: здесь действительно сравниваются оба разрешённых значения.

## 15. Пункт задания: свой полезный generic

**Где показать:** `src/utils/toArray.ts` и последние строки функций в `src/api/advice.ts`.

```ts
export function toArray<T>(value: T | T[]): T[] {
  return Array.isArray(value) ? value : [value]
}
```

**Как объяснить:**

> Компоненту нужен список, а сервис присылает один совет. Я сделал общую функцию: если ей передали список, она возвращает список. Если одно значение, делает список из одного элемента.
>
> T означает тип элемента. Для совета это Advice. Для строки мог бы быть string. Функция одна, но связь между входом и результатом сохраняется.

Вот настоящее использование:

```ts
return toArray<Advice>({ id: 'owl', text: data.advice })
```

**Как прочитать скобки:**

> В угловых скобках я передаю тип, а в круглых само значение. Здесь говорю: работаем с Advice, и передаю объект совета. Получаю Advice[].

Это как раз центральная идея небольшого generic-примера в лекции: один алгоритм не должен терять тип переданного элемента.

**Важное различие:** `useState<...>` использует уже готовый generic React. А `toArray<T>` - собственная generic-функция. Для пункта на 5 в проекте есть именно собственная функция, которая реально вызывается.

## 16. Пункт задания: Promise<T> и тип ошибки

**Где показать:** `src/api/advice.ts`, `src/api/saved.ts`, `src/utils/errors.ts`.

```ts
export function getErrorMessage(error: unknown): string {
  return error instanceof Error ? error.message : 'Произошла неизвестная ошибка.'
}
```

**Как объяснить Promise:**

> Запрос не может мгновенно вернуть ответ сервера. Он возвращает Promise - будущий результат. У Promise<Advice[]> после успешного await получится массив советов.

**Как объяснить ошибку:**

> Но запрос может закончиться неудачно. Поэтому ошибку тоже нельзя бездумно читать как готовый объект. Я принимаю unknown, проверяю instanceof Error и только тогда беру message. Если пришло что-то другое, использую запасной текст.

**Деталь лекции:** `Promise<Advice[]>` описывает успешный результат. Он не говорит, что ошибок не бывает, и не задаёт тип исключения вторым параметром.

**Где ошибка запроса становится видимой:** она доходит до Query, затем хук создаёт состояние error, и карточка показывает сообщение с повтором.

**Почему в Axios тоже есть проверка:** там сначала вызывается `axios.isAxiosError<unknown>(error)`. Только после этого мы пользуемся специфическими полями Axios-ошибки. Тело её ответа всё равно проверяется отдельно.

## 17. Пункт задания: ReactNode и ComponentProps

**Где показать:** `src/shared/Button.tsx` и переменную content в `src/components/AdviceResult.tsx`.

```tsx
import type { ComponentProps, ReactNode } from 'react'

type ButtonProps = ComponentProps<'button'> & { children: ReactNode }

export function Button({ children, type = 'button', ...props }: ButtonProps) {
  return <button type={type} className="retro-button" {...props}>{children}</button>
}
```

**Как объяснить:**

> У обычной HTML-кнопки уже есть готовое описание свойств: disabled, onClick, type и другие. Я беру его через ComponentProps, а не переписываю всё вручную.
>
> Children - это то, что находится внутри Button. ReactNode подходит для содержимого, которое React умеет показать: например, текста или JSX.

**Почему не string для children:** потому что допустимое содержимое шире одной строки. В будущем там может быть текст вместе с элементом.

**Как оно работает:** Button получает стандартные свойства и передаёт их обычному button. Внутрь вставляет children. Типы помогают проверить допустимые свойства, но сама передача выполняется обычным кодом.

В карточке `ReactNode` используется для content: в разных состояниях там может быть сообщение, блок с кнопкой или массив компонентов.

Связь с лекцией: типы событий, содержимого и стандартных элементов уже есть у React и браузерных описаний. Сначала ищем подходящий готовый тип, а не создаём свой огромный список свойств.

## 18. Пункт задания: discriminated union с полем-меткой

**Где показать:** `src/components/AdviceResult.tsx`.

**Как объяснить без сложного названия:**

> Смотри, у меня несколько вариантов ответа. Чтобы различать их, в каждом есть status. Если status равен success, значит в этом варианте есть data. Если error, значит есть сообщение ошибки. Поэтому сначала смотрю на status и только потом читаю нужное поле.

Ниже полный рабочий блок выбора содержимого из компонента:

```tsx
switch (result.status) {
  case 'loading':
    content = <p role="status">Сова ещё прыгает. Мысль на подходе...</p>
    break
  case 'error':
    content = <div role="alert"><p>{result.error}</p><Button onClick={onRetry}>Повторить</Button></div>
    break
  case 'empty':
    content = <p>Ответ пришёл, но советов нет. Даже сове нечего добавить.</p>
    break
  case 'success':
    content = result.data.map(item => <AdviceText key={`${item.id}:${item.text}`} source={result.id} text={item.text} />)
    break
}
```

Этот блок находится внутри компонента, где уже объявлены result, content и onRetry. Его не нужно запускать отдельно от компонента.

**Что назвать после объяснения:**

> Такую запись называют discriminated union: варианты различаются по общей метке. В моём случае эта метка status.

**Почему это лучше мешка необязательных полей:** если просто написать в одном объекте необязательные data и error, связь с состоянием будет потеряна. Поле могло бы отсутствовать даже в success. Здесь описание требует массив именно в успешном варианте.

**Деталь дополнительной части лекции:** switch сам по себе не во всех случаях гарантирует, что при добавлении нового варианта разработчик обязательно получит ошибку о пропущенной ветке. Для отдельной проверки полноты можно использовать never. В нашем компоненте такого дополнительного приёма нет; здесь показываем сужение типа по status.

## 19. Пункт задания: noUncheckedIndexedAccess и noUnusedLocals

**Где показать:** `tsconfig.json`, `src/components/Owl.tsx`.

```tsx
const idle: OwlMoment = { x: -1045, y: -410, text: 'Сова попалась. Теперь послушаем, что скажет.' }
const moment = loading ? moments[step] ?? idle : idle
```

**Как объяснить первый флаг:**

> Если я беру элемент массива по номеру, его там может не оказаться. Поэтому компилятор напоминает про undefined. У меня для такого случая есть запасная поза idle.

`??` выбирает запасной объект, если слева null или undefined.

**Почему TypeScript не успокоился от вычисления индекса по кругу:** проверка типов не доказывает все арифметические свойства алгоритма. Мы всё равно учитываем возможность отсутствующего элемента.

**Как объяснить второй флаг:**

> Если я создал переменную или импорт, а потом нигде не использовал, компилятор об этом сообщает. Так не остаются забытые куски после переделки кода.

Связь с лекцией: чтение словаря по ключу тоже может вернуть отсутствие значения. Механизм похож на чтение массива по индексу: нужно понимать, гарантировано ли там что-нибудь лежит.

## 23. Детали лекции: что ещё важно уметь объяснить

Ниже собраны небольшие различия, которые легко перепутать. Они не требуют добавлять новые функции в проект. Их нужно понимать, чтобы объяснить собственное решение.

### 23.1. Проверка до запуска и проверка во время работы

**Как объяснить:**

> До запуска TypeScript смотрит на исходники. Во время работы обычные if проверяют конкретные пришедшие значения. Это две разные проверки, и обе полезны.

Успешная проверка типов не означает, что нейросеть доступна. Успешный ответ нейросети не означает, что все props в остальных компонентах написаны правильно.

### 23.2. Типы исчезают, действия остаются

**Как объяснить:**

> Когда сайт собирается, записи interface и типы у параметров убираются. А функция, Number, typeof, запрос и условия остаются. Браузер выполняет именно эти действия.

В нашем типе есть `number | null`, но преобразует строку функция `Number`, а не вертикальная черта и не слово number.

### 23.3. Простые типы и массивы

**Как объяснить:**

> string - текст, number - число, boolean - да или нет. Advice[] - список советов. Я использую маленькие имена string и number, а не объекты-обёртки String и Number в описании типов.

У функции `Number(text)` большая буква, потому что это уже реальная функция JavaScript для преобразования. Здесь не описание типа.

### 23.4. Вывод типов и явная запись

**Как объяснить:**

> Если я написал useState(''), уже понятно, что это строка. Если будущие варианты шире первого значения, подсказываю их явно. Так получилось с number или null.

Небольшое количество аннотаций не означает отсутствие проверки. TypeScript много информации получает из контекста.

### 23.5. Вопросительный знак, точка и двойной вопросительный знак

В `OwlMoment` есть:

```ts
width?: number
```

**Как объяснить:** это строка из interface, которая разрешает полю width отсутствовать.

В клиенте есть:

```ts
const data = error.response?.data
```

**Как объяснить:** если response отсутствует, не пытаюсь читать у него data, а получаю undefined.

В выборе позы есть:

```ts
const moment = loading ? moments[step] ?? idle : idle
```

**Как объяснить:** если во время загрузки нужной позы нет, беру запасную.

Это три разных применения похожих символов. Необязательное поле описывается в типе. Операторы `?.` и `??` выполняются как JavaScript и остаются в работающей программе.

### 23.6. Описание объекта не создаёт объект

**Как объяснить:**

> Interface говорит, какие поля должны быть. Но сам совет появляется только когда я получил данные и создал объект. От записи interface новый совет не возникнет.

То же относится к type и утилитам Pick/Omit. А вот `sourceNames` является настоящим объектом и существует во время работы.

### 23.7. Совместимость по полям

Это дополнительная тема лекции о том, как TypeScript сравнивает объекты.

**Как объяснить:**

> Обычно важно, какие у объекта есть поля и какие у них типы. Подходящий объект не обязан быть создан специальным конструктором Advice. Это не класс с обязательным созданием через new.

Не говори, что тип всегда требует точного отсутствия любых лишних полей. Для свежих объектных литералов есть отдельная проверка лишних свойств, а обычная совместимость объектов в целом устроена по необходимой структуре.

### 23.8. Тип события иногда можно не писать вручную

В нашей форме обработчик textarea записан прямо в JSX:

```tsx
onChange={event => onQuestionChange(event.target.value)}
```

Это свойство элемента textarea внутри компонента, а не самостоятельная программа.

**Как объяснить:**

> Здесь TypeScript уже знает, у какого элемента указан onChange, и выводит тип event. А у отдельно объявленной handleLimitChange я указываю ChangeEvent<HTMLInputElement> явно.

### 23.9. FormEvent и ChangeEvent решают разные задачи

**Как объяснить:**

> ChangeEvent нужен, когда изменилось значение поля. FormEvent нужен, когда отправили форму. В отправке я вызываю preventDefault, чтобы браузер не перезагрузил страницу обычной HTML-отправкой.

Сами названия типов не проверяют непустой вопрос и допустимое число. Для этого нужны отдельные условия.

### 23.10. Готовый тип библиотеки не надо изобретать заново

**Как объяснить:**

> Я не описываю все свойства input или button сам. Для элементов и событий уже есть готовые типы. Поэтому для кнопки взял ComponentProps, для события ChangeEvent, для содержимого ReactNode.

DOM-типы относятся к браузерным элементам. Типы React используются для React-событий и компонентов. Обычный Promise не нужно импортировать из React.

### 23.11. Свой хук остаётся функцией

**Где показать:** конец `src/hooks/useAdvice.ts`.

```ts
return { results, loading: results.some(result => result.status === 'loading'), reload }
```

Это возвращаемый объект внутри хука.

**Как объяснить:**

> Хук собирает результаты, общий флаг загрузки и функцию повтора. TypeScript видит, из каких типизированных значений собран объект, и сам выводит тип результата. Поэтому компоненты получают уже известные поля.

В лекции есть дополнительный пример явного именованного результата собственного хука. У нас результат выводится автоматически из уже описанных данных. Не нужно утверждать, что любой хук обязательно должен иметь отдельный interface результата.

### 23.12. useEffect не требуется превращать в generic

**Где показать:** таймер в `src/components/Owl.tsx`.

**Как объяснить:**

> Эффект запускает таймер, пока идёт загрузка. Когда загрузка заканчивается или компонент убирается, функция очистки удаляет таймер. Типы результата эффекта React уже знает, поэтому я не добавляю ему свой параметр типа.

Дополнительный материал лекции также напоминает: callback эффекта не делают напрямую async, потому что async возвращает Promise, а эффект ожидает очистку или отсутствие возвращаемого значения. В нашем эффекте сети нет, только таймер.

## 24. Что есть в дополнительных материалах лекции, но не требуется притягивать к коду

Уметь объяснить отсутствие лишнего инструмента тоже полезно. Не говори, что применил всё, что встретилось в лекции.

| Тема | Как объяснить просто | Что у нас |
| --- | --- | --- |
| `readonly` и `Readonly` | Запрещают изменять поля через соответствующий тип; объект от этого не замораживается в JavaScript | Отдельный приём readonly не добавлялся |
| `Partial` | Делает поля в описании необязательными, когда нужно передать только часть изменений | Для нашего добавления совета обязательны source и text, поэтому не нужен |
| `Extract` и `Exclude` | Позволяют выбрать или убрать варианты из уже существующего union | Небольшие варианты написаны напрямую |
| `NonNullable` | Убирает null и undefined из описания типа; саму проверку значения не выполняет | Используются реальные проверки null |
| `ReturnType` | Позволяет взять тип результата функции из её описания | Для небольших функций достаточно вывода и явных Promise |
| Ограничение generic через extends | Требует, чтобы T имел необходимые поля | toArray не читает поля элемента, поэтому ограничение ему не нужно |
| `keyof` и связанный тип ключа | Не дают запросить поле, которого нет в описании объекта | Сложная универсальная функция чтения поля проекту не понадобилась |
| `never` | Помогает проверить, что после разбора вариантов ничего не осталось | Отдельная проверка полноты switch через never не добавлена |
| `useRef` с типом элемента | Позволяет обращаться к конкретному DOM-элементу после его появления | Для существующей логики отдельный ref не нужен |

Это дополнительные знания для вопросов. Основные пункты на оценку 5 реализованы без добавления всех перечисленных механизмов.

## 26. Разговорная защита целиком, если нужно связать пункты

> Смотри, я взял тот же сайт с совой. Раньше части программы просто передавали друг другу значения, а теперь я описал, какими эти значения должны быть.
>
> Начал с совета. У него есть id и текст. У сохранённого есть ещё источник. Источник разрешён только один из двух. Поэтому опечатка в его названии теперь заметна ещё при проверке кода.
>
> Дальше описал то, что получают компоненты. Например, форма получает строку вопроса и функцию, которой отдаёт новую строку. Так она не может случайно передать в обработчик неподходящее значение.
>
> Но с сервером одного описания недостаточно. Поэтому я получаю неизвестные данные и проверяю их. Если всё подошло, создаю совет нужного вида. Если нет, показываю ошибку. Просто написать as и поверить ответу я не стал.
>
> Для карточки описал отдельные варианты: загрузка, ошибка, пустота и успех. Внутри успеха есть массив, внутри ошибки сообщение. Потом смотрю на status и выбираю, что рисовать. Так я не пытаюсь показать данные, которых ещё нет.
>
> Для списка использовал маленькую общую функцию toArray. Она превращает один совет в массив и сохраняет его тип. Это мой собственный generic, который действительно вызывается в запросах.
>
> В копилке добавил количество показываемых записей. Из input приходит строка. Я превращаю её в число и проверяю, что оно целое и от 1 до 50. Если ввод неправильный, храню null и показываю сообщение.
>
> Для общей кнопки взял готовые типы React, а не описывал заново все её свойства. Ещё включил строгие настройки и обработал возможное отсутствие значений.
>
> В конце запускаю проверку типов. Могу специально написать неправильный источник cat, получить понятную ошибку, исправить на owl и показать, что проверка снова проходит.

## 27. Быстрая памятка перед защитой

Для каждого механизма отвечай на три вопроса:

1. Что приходит на вход?
2. Что я проверяю или делаю с этим значением?
3. Что получает следующая часть программы?

Например, у числового поля: приходит строка, я преобразую и проверяю её, список получает число либо состояние ошибки. У API: приходит неизвестный ответ, я проверяю его поля, карточка получает проверенный совет. У состояния: приходит status, я выбираю ветку, пользователь видит подходящее содержимое.

Если застрял на термине, вернись к этим трём вопросам. Они связывают определения из лекции с настоящей работой твоего сайта.
