# Лабораторная 8: как объяснить работу простыми словами

Это подсказка для защиты моего проекта «Сова на скакалке».
Объяснения привязаны к моим файлам и к
[лекции по тестированию](https://ngg-dev.github.io/lecture-frontend/lectures/testing-lecture/).
Примеры магазина из лекции я не переносил в проект: проверяю свои советы и копилку.

## 1. Что я сделал

Можно начать так:

«У меня уже был сайт с советами на TypeScript. В этой работе я добавил проверки.
Маленькие функции проверяю через Jest, а действия на сайте через Playwright.
Например, могу проверить, что один совет превращается в массив.
А могу открыть сайт, сохранить совет и проверить, что он появился в копилке».

Сам сайт для лабораторной не переписывался. Изменились настройки,
зависимости, команды запуска и тесты. Старые проверки сервера сохранены.

## 2. Зачем тесты, если есть TypeScript

В лекции это тема «TypeScript не знает, какую скидку обещали».

«Типы проверяют, что я работаю с подходящими данными. Но подходящие по типу
данные могут быть неправильными по смыслу. Например, функция должна вернуть
массив с одним советом, а вернет пустой массив. Для TypeScript оба результата
могут быть массивами строк. Тест сравнит результат с тем, который мы ожидали».

Тестирование и проверка данных во время работы тоже решают разные задачи.
Проверка `readSavedAdvice` защищает приложение от неверного ответа сервера.
Тест проверяет саму эту защиту на заранее выбранных примерах.

## 3. Что такое unit и e2e

В лекции это темы «Что проверяют unit и E2E» и «Инструмент появляется после задачи».

| Проверка | Простое объяснение | Мой пример |
| --- | --- | --- |
| Unit | Вызываю отдельную небольшую функцию и проверяю ответ | `toArray('Совет')` дает `['Совет']` |
| Асинхронный unit | Проверяю функцию, которая получает результат не сразу | `getSaved` возвращает советы после ответа HTTP-клиента |
| E2E | Открываю приложение в браузере и выполняю действия человека | Ввожу вопрос, сохраняю ответ и открываю копилку |

«Если маленькая функция работает, это еще не значит, что кнопка на странице
правильно ее вызывает. Поэтому я проверил и функции, и путь через интерфейс».

В лекции есть также компонентные тесты с Testing Library.
В этой работе их нет: отдельного требования на них в PDF нет.
Поведение формы проверяется в браузерных сценариях Playwright.

## 5. Как устроен самый маленький тест

Открываю `tests/utils.test.ts`:

```ts
test('Одно значение превращается в массив', () => {
  expect(toArray('Совет')).toEqual(['Совет'])
})
```

«У теста есть название и действие. Я передаю строку в настоящую функцию
`toArray`. Потом говорю: ожидаю массив, в котором лежит эта строка.
Если функция вернет что-то другое, тест упадет».

- `test` объявляет одну проверку.
- Первый аргумент объясняет, что мы проверяем.
- `() => { ... }` содержит выполняемые действия.
- `toArray('Совет')` вызывает настоящую функцию из `src`.
- `expect` получает фактический результат.
- `toEqual` сравнивает содержимое результата с ожидаемым массивом.

Дополнительно проверяются уже готовый массив и пустой массив.
Это не отдельная новая функция, а разные входы для существующей.

## 6. AAA из лекции

В лекции есть «AAA: методология построения теста».
Это три шага: подготовка, действие, проверка.
Никакую библиотеку AAA устанавливать не надо.

Вот пример из `tests/validation.test.ts`:

```ts
test('Правильный совет проходит проверку', () => {
  const advice = { id: '1', source: 'owl', text: 'Отдохни' }
  expect(readSavedAdvice(advice)).toEqual(advice)
})
```

«Сначала я подготовил объект совета. Потом передал его в проверку.
Потом сравнил полученный объект с тем, что должен получить.
В коде действие и сравнение записаны в одной строке, но по смыслу это два шага».

Ожидаемый результат я выбираю по правилу проекта: у совета есть строковый id,
разрешенный источник и текст. Я не переписываю ответ сломанной функции в тест,
чтобы получить зеленую галочку.

## 7. Как проверяются неверные данные

Открываю `tests/validation.test.ts`:

```ts
test.each([null, {}, { id: 1, source: 'owl', text: 'Совет' }, { id: '1', source: 'cat', text: 'Совет' }])(
  'Неверный совет %j отклоняется', value => {
    expect(() => readSavedAdvice(value)).toThrow('Копилка прислала непонятный ответ.')
  },
)
```

«Здесь одна схема проверки повторяется для четырех плохих значений.
Первое вообще null. Во втором нет полей. В третьем id является числом,
а должен быть строкой. В четвертом неизвестный источник cat.
Для каждого случая ожидаю ошибку».

- `test.each` запускает проверку отдельно для каждого значения списка.
- `%j` подставляет значение в название, чтобы было понятно, какой случай упал.
- `value` является текущим проверяемым значением.
- `() => readSavedAdvice(value)` передает Jest действие, которое может выбросить ошибку.
- `toThrow` проверяет, что ошибка действительно появилась и текст подходит.

«Стрелка здесь нужна, чтобы Jest сам вызвал функцию и поймал ошибку.
Если вызвать ее заранее, ошибка вылетит раньше самой проверки `toThrow`».

## 8. Как проверяется функция, которая ждет ответ

Открываю `tests/saved.test.ts`:

```ts
test('Загрузка возвращает список советов', async () => {
  jest.mocked(http.get).mockResolvedValue({ data: [advice] })
  expect(await loadSaved()).toEqual([advice])
})
```

«Сначала говорю подмененному HTTP-клиенту: верни такой ответ.
Потом вызываю загрузку. Она выполняет настоящую `getSaved`, получает
подготовленные данные, проверяет их и возвращает список.
После завершения сравниваю список с ожидаемым».

- `async` позволяет использовать `await` внутри теста.
- `jest.mocked` помогает TypeScript понимать, что метод используется как подмена.
- `mockResolvedValue` задает результат успешно завершившегося Promise.
- `{ data: [advice] }` повторяет нужную функции часть ответа Axios.
- `await` ждет завершения загрузки, а не просто создания Promise.
- `loadSaved` является маленькой оберткой над `getSaved`, которая передает `AbortSignal`.
- `AbortSignal` позволяет отменить запрос; в этом тесте отмена не проверяется.

«Без ожидания можно закончить тест раньше загрузки. Поэтому асинхронный
результат я обязательно жду».

## 9. Как проверяется ошибка загрузки

```ts
test('Ошибка загрузки передается дальше', async () => {
  jest.mocked(http.get).mockRejectedValue(new Error('Нет сети'))
  await expect(loadSaved()).rejects.toThrow('Нет сети')
})
```

«Тут я подготовил отказ вместо успешного ответа. Функция должна передать
ошибку вызывающему коду. `rejects` проверяет отказ Promise, а `toThrow`
проверяет сообщение. Само ожидание тоже асинхронное, перед ним стоит await».

Это соответствует теме лекции «Как проверить отказ, не ломая рабочий сервер?».
Нам не нужно отключать интернет или ломать сайт, чтобы проверить ошибку.

## 10. Что подменяется и почему это честная проверка

В начале файла есть:

```ts
jest.mock('../src/api/client', () => ({ http: { get: jest.fn(), post: jest.fn() } }))
```

«Я подменяю внешний источник данных, то есть HTTP-клиент.
Но `getSaved` и `saveAdvice` импортированы из настоящего файла приложения.
Именно их работу я хочу проверить».

`jest.fn()` создает управляемую функцию-подмену. В каждом тесте ей задается
свой ответ или своя ошибка. `mockResolvedValue` не обращается к настоящему серверу.

При сохранении проверяю и результат, и данные, которые ушли в клиент:

```ts
expect(await saveAdvice(draft)).toEqual(advice)
expect(http.post).toHaveBeenCalledWith('/api/saved', draft)
```

«Мне важно, что отправлены правильные данные по правильному адресу,
и что функция вернула сохраненный совет после проверки ответа».

Если бы я заменил саму `saveAdvice` и проверил, что подмена возвращает мой
объект, настоящий код сохранения вообще бы не выполнился. Такой тест
ничего не сказал бы о работе этой функции.

## 11. Как тесты не мешают друг другу

В Jest перед каждой проверкой выполняется:

```ts
beforeEach(() => jest.resetAllMocks())
```

«Это сброс подготовленных ответов и истории вызовов.
Потом каждый тест сам задает то, что ему нужно.
Успешный ответ из предыдущего теста не должен случайно попасть в следующий».

В Playwright каждый тест получает отдельный браузерный контекст.
Это отдельное состояние браузера. Тестовые записи для копилки тоже создаются
внутри конкретного теста. Один сценарий не требует предварительного запуска другого.

Но отдельный контекст не очищает настоящую серверную базу.
Поэтому в наших сценариях запросы копилки подменены и данные хранятся
в локальном массиве конкретного теста.

## 12. Что делает Playwright

Открываю `e2e/advice.spec.ts`.

«Playwright открывает страницу в Chromium и делает обычные действия:
вводит вопрос, нажимает кнопку, сохраняет совет, переходит в копилку.
После действий он проверяет, что на странице появился нужный текст».

Ключевые строки сценария:

```ts
await page.goto('/')
await page.getByLabel('Что тебя озадачило?').fill('Как подготовиться к защите?')
await page.getByRole('button', { name: 'Получить пернатый совет' }).click()
```

- `page` представляет открытую страницу браузера.
- `goto('/')` открывает главную относительно адреса из конфига.
- `getByLabel` находит поле по связанной с ним подписи.
- `fill` заполняет поле.
- `getByRole` ищет элемент по его роли и имени, здесь кнопку.
- `click` нажимает кнопку.
- `await` ждет выполнения действия.

Для карточки совы использую `.result-owl`, чтобы не нажать такую же кнопку
у карточки Канье. Для окончательной проверки использую `.saved-page`,
чтобы искать текст уже внутри страницы копилки, а не на предыдущей странице.

## 13. Три браузерных сценария

### Пустой вопрос

«Я открываю сайт и нажимаю отправку с пустым полем.
Должна появиться ошибка "Сначала напиши вопрос!".
Я проверяю результат на странице, а не только существование кнопки».

### Сохранение совета

«Я ввожу вопрос и получаю подготовленный ответ "Не спеши".
До отправки вопроса подмена возвращает другой текст, так что тест ждет
именно результат отправки. Потом сохраняю совет и вижу заблокированную
кнопку "Сохранено". Открываю копилку и проверяю наличие того же текста».

Внутри этого теста создан массив `saved`.
При POST подмена берет отправленные данные, добавляет id и кладет совет в массив.
При GET подмена возвращает этот массив. Это небольшое управляемое хранилище
только на время одной проверки, а не настоящая база данных.

### Исправление лимита

«В копилке сначала есть один совет. Я ввожу 0, хотя разрешено от 1 до 50.
Проверяю сообщение об ошибке и отсутствие советов на экране.
Затем ввожу 1. Ошибка пропадает, совет снова виден».

Это проверяет не только отказ, но и возможность продолжить работу после исправления.

## 14. Почему нет пауз через несколько секунд

В лекции это тема про надежные ожидания браузера.

```ts
await expect(page.locator('.saved-page').getByRole('blockquote')).toHaveText('Не спеши')
```

«Проверка Playwright повторяется, пока не появится нужный результат или
не закончится время ожидания. Я не угадываю, за сколько секунд загрузится
страница на другом компьютере. Поэтому искусственного sleep в тестах нет».

`await expect` является ожиданием результата. Это отличается от простого
ожидания фиксированного количества секунд, после которого страница
все равно может быть не готова.

## 15. Как проверяется сайт с хостинга

Открываю `playwright.hosted.config.ts`.

«Обычный конфиг сам запускает локальный сайт.
В конфиге для защиты локальный сервер отключен через `webServer: undefined`.
Адресом `baseURL` указан мой опубликованный сайт.
Поэтому тот же `goto('/')` открывает главную с хостинга».

В этом конфиге также включены `trace: 'on'` и `screenshot: 'on'`.
Сохраняются шаги проверки и снимок страницы, чтобы можно было разобрать результат.

Важно объяснить честно:

«Страницы и код сайта загружаются с хостинга. Ответы API подготовлены тестами.
Так можно проверить интерфейс независимо от ключа и бесплатной квоты.
Эти сценарии не доказывают, что настоящий OpenRouter сейчас доступен
или что данные записались в рабочую базу».

## 16. Как показать запуск на другом компьютере

Нужны Node.js 24, интернет и актуальная папка проекта с новыми тестами.
Одной ссылки на опубликованный сайт для запуска тестов недостаточно.

Подготовка:

```bash
npm ci
npx playwright install chromium
```

Jest:

```bash
npm test
```

Playwright с сайтом на хостинге:

```bash
npm run test:e2e:hosted:ui
```

В окне нажимаю Run all. Затем выбираю конкретный тест слева.
В Actions выбираю действие после открытия страницы и вкладку After,
чтобы показать состояние сайта после действия. Если справа about:blank,
сначала выбираю тест и шаг. До выбора просмотр может быть пустым.

Если нужен обычный видимый браузер с автоматическим запуском:

```bash
npm run test:e2e:hosted:headed
```

Если нужен вывод команд для отчета, открываю `testsout` в корне проекта.
Там сохранен реальный повторный запуск, команды и коды их завершения.
Код 0 означает, что команда завершилась успешно.

## 17. Как доказать, что тест способен заметить ошибку

В лекции это темы «Докажите, что тест ловит нужную ошибку» и
«Проверьте тест, который написал ИИ».

«Раньше я временно заставил `toArray` всегда возвращать пустой массив.
Проверка обычного значения упала, потому что ожидала массив с советом.
После восстановления функции проверки снова прошли».

Эта пробная поломка уже исправлена. Для повторной демонстрации можно
локально изменить только результат `toArray`, выполнить `npm test`,
увидеть падение и сразу вернуть правильную функцию.
После восстановления нужно снова выполнить `npm test`.
Не надо менять ожидаемый результат теста на неправильный ради зеленого цвета.

## 18. Почему я не стремился проверить каждую строчку

В лекции есть тема «100% строк - не 100% обещаний».

«Мне важнее проверить полезное поведение: неверный совет отклоняется,
ошибка загрузки не теряется, сохраненный совет появляется в копилке.
Просто проверить, что кнопка существует, было бы недостаточно.
Тесты выбраны короткие, чтобы я мог объяснить каждую проверку».

Зеленые тесты не означают, что ошибок вообще нет.
Они означают, что выбранные сценарии прошли на выбранных условиях.
Например, отдельной проверки нагрузки или настоящей общей базы в них нет.

## 19. Что означают файлы настроек

| Файл | Что сказать простыми словами |
| --- | --- |
| `package.json` | Здесь зависимости и короткие команды запуска |
| `package-lock.json` | Закрепляет дерево зависимостей для повторяемой установки через npm ci |
| `jest.config.cjs` | Говорит Jest, где лежат тесты и как прочитать TypeScript |
| `playwright.config.ts` | Говорит Playwright, где тесты и как запустить локальный сайт |
| `playwright.hosted.config.ts` | Меняет адрес на сайт с хостинга и отключает локальный сервер |
| `.gitignore` | Исключает автоматически созданные браузерные отчеты и результаты |

В конфиге Jest:

- `testEnvironment: 'node'` подходит для функций, которым не нужен браузер.
- `testMatch` выбирает новые файлы `tests/*.test.ts`.
- `moduleNameMapper` объясняет путь `@/`, используемый в приложении.
- `babel-jest` подготавливает TypeScript к выполнению Jest.
- TypeScript-синтаксис убирается при преобразовании; полноценную проверку типов приложения делает отдельная команда `npm run typecheck`.
- `clearMocks` очищает историю вызовов, а `resetAllMocks` в тестах дополнительно сбрасывает заданные реализации подмен.

Старые `tests/owl.test.js` запускаются через `npm run test:server`.
Это прежние серверные проверки на встроенном инструменте Node.js.
Они сохранены дополнительно. Требование новой лабораторной на Jest выполняют

## 20. Короткий порядок защиты

1. Открываю сайт с совой и объясняю, что он делает.
2. Открываю `tests/utils.test.ts` и объясняю один самый маленький тест.
3. Показываю неверные входы в `tests/validation.test.ts`.
4. Показываю в `tests/saved.test.ts` один успех и одну ошибку с await.
5. Объясняю, что подменен HTTP-клиент, а не функция сохранения.
6. Запускаю `npm test` или показываю его реальный вывод в `testsout`.
7. Запускаю Playwright для хостинга и показываю сценарий копилки.
8. Называю границу проверки: интерфейс настоящий, ответы API подготовленные.
9. Показываю в `testsout` результаты проверки типов и сборки.

## 21. Короткие ответы на вопросы

**Что такое mock?**
Управляемая подмена внешней зависимости. Я сам задаю ей ответ или ошибку.

**Почему тесты без настоящего API?**
Чтобы проверить свой код повторяемо, без ключа, квоты и случайного ответа сервиса.

**Что означает expect?**
Я передаю полученный результат и затем задаю, каким он должен быть.

**Чем отличаются toBe и toEqual?**
`toBe` сравнивает значения через Object.is; для объектов это проверка той же ссылки.
`toEqual` сравнивает содержимое массивов и объектов. Поэтому массив советов
обычно проверяю через toEqual, а сохранение той же ссылки через toBe.

**Почему в тесте ошибки написана стрелочная функция?**
Чтобы Jest сам выполнил действие и проверил выброшенную ошибку.

**Что такое Promise?**
Результат операции, которая завершится позже: успешно или с ошибкой.

**Что делает await?**
Ждет завершения Promise. При отказе ошибка передается дальше,
а в тесте `rejects` позволяет проверить такой отказ.

**Зачем beforeEach?**
Подготовить одинаковое чистое начало для каждой проверки.

**Что такое регрессия?**
То, что работало, сломалось после изменения кода. Повторяемый тест помогает это заметить.

**Почему одного unit-теста мало?**
Он не проверит, что форма, кнопка, переход и список правильно работают вместе.

**Что покажет Playwright?**
Результат действий через настоящий интерфейс в браузере.

**Доказывает ли зеленый тест работу настоящей базы?**
Нет. В наших браузерных сценариях ответы копилки подменены.

**Где настоящий вывод запуска?**
В `testsout` в корне проекта. Там указаны команды и результаты их выполнения.
